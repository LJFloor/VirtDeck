# Terminal

`TerminalModule` is one shell on the SSH host, as the account the user logged in with, drawn by the same `TerminalControl` the container console and the container log window use, over the same `SshPtySession`. Every other module wraps a command (`virsh`, `docker`, `dd`); this one is the host itself, so anything the UI does not model no longer means leaving VirtDeck with the credentials in hand.

- **The login user's shell, not root, and that needed a second factory.** `SshPtySession.Open` wraps its argv in `exec sudo -S -p '<marker>' ...` unconditionally, so every session it makes is a root one and its gate, marker and preamble exist to hide sudo's prompt and the login shell running it. A host terminal wants none of that: the MOTD and the prompt **are** the content. So `SshPtySession.OpenShell` (behind `OpenShellPtyAsync`) asks for a plain SSH shell, which already runs the account's own shell, with no argv, no bootstrap line, no sentinel and the gate open from the first byte. `sudo` typed into it prompts the user normally, and the sudo password VirtDeck holds is never written into this session.
- **Echo is the trap.** `Open` sets `ECHO = 0` because the line it types and the sudo password that may follow are the client's, and `docker exec -it` echoes for itself inside the container. There is nothing downstream of a plain login shell to do that, so copying the modes here would mean typing into a shell that shows nothing back. `OpenShell` uses the overload that takes no modes at all.
- **`Deactivate` deliberately does nothing but stop the resize debounce.** This is the one module that costs something while hidden, and that is the whole feature: the PTY read thread keeps feeding `TerminalScreen` under its own lock, so a `tail -f` left running is still running on the way back. Nothing needs the UI thread on that path, and `TerminalControl` stops only its 16 ms pump on detach, so re-attaching catches up in a single repaint against the stale `_drawnRevision`. `Shutdown` **must** end the session, because the shell disposes the shared connection straight after.
- **Auto-start once, then stay dead.** `ActivateAsync` opens the shell the first time the module is looked at and never again: coming back to a live session must not disturb it, and coming back to one the user ended by typing `exit` must not silently revive it. There is no window to close here, so a clean exit leaves the last screen with a line saying so and Reconnect enabled; a failure reads the same way with its own reason. That is the opposite of `ContainerConsoleWindow`, which closes on a clean exit precisely because it *is* a window.
- **The status bar is the module's two slots, so there is no footer.** Left says what the session is doing, right says `user@host` (with the port only when it is not 22), which needs no probe: the connection already knows. The toolbar is **Reconnect and nothing else**: copy, paste and the font size are gestures the terminal already has (`Ctrl+Shift+C`/`V`, `Ctrl+wheel`), and a button that only repeats one is a button in the way of the shell. Reconnect is not `Classes="accent"`, which is reserved for the one command that creates something.

## Terminal keyboard handling (three surfaces, and why one has no handler)

**`ContainerLogsWindow` deliberately registers none of this.** The tunnelled handler exists because Tab and the arrow keys would otherwise drive the toolbar or footer buttons instead of reaching the far end; a read-only surface has no far end, so Tab walking to Reload and the buttons beside it is exactly the right behaviour there. It keeps `Ctrl+Shift+C` alone, as a **plain bubbling** handler, which reaches it because `HandleKey` answers false for the chord on a read-only surface rather than consuming it. `Ctrl+C` does not become copy there just because that window has nothing to interrupt: the two consoles are the muscle memory it shares.

For the two that do talk back, the keyboard handler is registered on the **top level**, tunnelled and `handledEventsToo`, exactly as `ConsoleWindow` does for the guest: without it Tab moves focus to the toolbar or footer buttons and the arrow keys drive them, so neither ever reaches the far end. `TerminalModule` registers in `OnAttachedToVisualTree` and removes in `OnDetachedFromVisualTree`, so another module's Tab stays its own; `ContainerConsoleWindow` forwards only while the terminal has focus, so its buttons stay usable, and no button on that bar carries `IsDefault` or `IsCancel` because Enter and Escape belong to the container. `Ctrl+Shift+C`/`V` are the two chords kept, because Ctrl+C already means interrupt. Printable text arrives through `TextInput`, so dead keys, compose and any layout work with no table to maintain; `TextInput` carries no modifiers, so the key press that preceded it is what says whether it was a chord and was already sent.
