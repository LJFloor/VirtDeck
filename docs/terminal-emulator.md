# Terminal surfaces: container logs, the container console and the emulator

## Reading a container's log

`ContainerLogsWindow`, one per container, over `DockerService.TailLogsAsync` and `IsRunningAsync`. Non-modal and outliving a module switch, like a `ConsoleWindow`, so `ContainersModule` keeps the handles and closes them in `Shutdown`. There is no state gate on the menu item: a stopped container's output is exactly what somebody comes to read.

- **The display is `TerminalControl`, read-only, and not a `TextBox`.** A container's output *is* a terminal's output, so drawing it as plain text was printing escape sequences instead of obeying them: an image that colours what it prints came out as `ESC[31m` runs, and anything redrawing a line with a carriage return left its fragments stacked. It also ends a second display for a thing the app already draws, and replaces a megabyte of text re-materialised into a `TextBox` on every 120 ms tick, unvirtualised, with a cell grid the repaint pump touches only when the revision moved. **The one thing it must not cost is the unwrapped record**, which is what the box it replaced was for, and `TerminalControl.WrapColumns` is the answer: the screen is **512 columns wide whatever the window is**, so a record runs off to the right exactly as it did, a horizontal scroll bar below the terminal reaches it, and only a record longer than that folds. Turning autowrap off instead would truncate, with nothing to scroll to for the rest. Folding is the wrong failure here in a way it is not in a console: a folded record is indistinguishable from the next record.
- **A screen wider than the window is paid for by trimming history, not by the window.** A line costs its width in cells while it is on screen, so 512 columns would be 61 MB at a full scrollback if history kept the padding. It does not: `TerminalScreen` cuts a line's trailing blanks as it leaves the screen, which is safe for the reason `Resample` already states, that a history line is only ever drawn and every reader stops at the line's own length rather than at `Cols`. The one thing that puts a history line back on the screen is a `Resize` growing downwards into it, and that resamples what it pulls back to the full width. A line then costs what was printed on it, so the console and the terminal module got the same saving on the way past, and the old "history costs window width" reading is simply gone. Two smaller things follow from the fixed width: narrowing the window no longer calls `Resize` at all, so the tail of a line captured wider is no longer lost until a Reload; and a selection over history is now ragged at the right rather than square, because there are no blanks out there to highlight.
- **The horizontal bar is sized from the widest line, not from `WrapColumns`.** `TerminalScreen.MaxUsedColumns` is one past the rightmost column anything has been printed at, so a log of ordinary records does not offer four hundred columns of blank to scroll through. It only grows within a session: once the widest line has fallen out of history it overstates, and `Reset` is what puts it back, which is what Clear and Reload already do. Shrinking it honestly would mean measuring every line on every scroll, to save a bar from being longer than it needs to be. The repaint pump watches it exactly as it watches `ScrollbackCount`, and for the sharper version of the same reason: nothing announces a wider line, and once the history is full the line count stops moving altogether, so watching that alone would freeze the horizontal bar.
- **`TerminalControl.ReadOnly` is a property of the surface, where `Live` is a property of the session.** That is why they are two flags and not one: `Restart()` puts `Live` back, because a reconnect is a new session, and must not touch `ReadOnly`, because a reload is still the same read-only window. `ReadOnly` gates `Send` (so keystrokes, paste **and the parser's own replies** stop, which `Live` never covered), draws no cursor, and **takes the mouse away from the far end**. That last one is not tidiness: a log is content somebody else wrote, and an `ESC[?1002h` in it would otherwise swallow pointer presses and silently stop the text being selectable, to send reports nowhere. It is said once, by `MouseState()` answering `Off`, because every pointer path already tests for that. The scrollback keys sit **above** the gate, so a read-only surface and a dead session can both still page through history, which the wheel always could.
- **A read-only surface holds its place instead of snapping to the bottom.** A console snaps because what the far end prints is the thing worth looking at; a log is being *read*, and yanking the view to the newest line on every arriving line is what made the old box's scroll bar useless while following. `Receive` advances the offset by however many lines the feed appended. It holds only **while the history is still growing**: past `MaxScrollback` an old line is dropped for each one added, the delta is zero, and the view drifts, because the lines it was showing are genuinely gone.
- **A container can put the log window on the alternate screen**, and this is a documented omission rather than an oversight. Anything run under `-t` writes `ESC[?1049h`, `docker logs` replays it, and the parser obeys: scrollback reads 0, the bar disables and the wheel stops. **Clear** is the way out, because it is `Reset()`, which is RIS and drops the alt screen along with any pen colour or mouse mode a stray sequence left behind; Reload is the other. Defending against it in Core would mean teaching `TerminalScreen` about an input it is right to obey everywhere else.
- **`Clear` is `ClearScreen()` and `Reload` is `Restart()`, and the difference is the parser, not the screen.** Clear runs with the stream still live, where dropping the parser would cut it mid escape sequence and corrupt the very next line. Reload cannot keep it: `StopStream` cancels `docker logs` wherever it happens to be, so a parser left partway through a sequence would eat the first bytes of the new stream.
- **`Live` is left alone for the window's whole life.** There is no session here, `ReadOnly` is what keeps it from sending, and setting `Live` false would buy nothing while costing the reader the history paging they came for.
- **Bare `\r` progress lines stay one row each**, inherited rather than introduced: `StreamReader.ReadLine` treats a lone `\r` as a terminator, so the information is destroyed inside `RunSudoCommandStreaming` before `TailLogsAsync` sees it. The `TextBox` had the identical flaw through `AppendLine`. Fixing it means a byte-level streaming API.
- **Lines are fed as `\r\n` and never `\n`.** `TerminalScreen.LineFeed` moves down only and the parser has no LNM mode, so a bare LF starts every record at the column the one before it ended in and draws the whole log as a staircase. It is the single most likely thing here to be "simplified" wrongly.

- **`2>&1`, inside the inner `bash -c`.** `docker logs` demultiplexes the container's two streams back onto the CLI's stdout and stderr, and `RunSudoCommandStreaming` reads **stdout only**, so without the redirect an image that logs to stderr (most of them) shows an empty window. It goes inside the `bash -c` rather than on the `sudo` so sudo's own stderr is not merged into the log.
- **It always follows, and the Follow checkbox is gone.** It read as a toggle for the *view*, which is what nearly every log viewer means by the word, and that half became unconditional the moment a scrolled-up reader kept their place: the view follows the newest line while it is sitting at the bottom and holds still otherwise, so there was nothing left for a user to ask it for. What the checkbox actually controlled was the **stream**, and losing that has one real cost, stated in the markup rather than glossed: a chatty container goes on evicting history under a reader who has scrolled up, because `MaxScrollback` is 5000 lines and past that an old line is dropped for each one arriving, so unticking was the only thing that could freeze what was on screen. **Reload** is what restarts from the top, and it throws the screen away first, because a reload replays the same `--tail 1000` history and appending it would show every line twice. `DockerService.TailLogsAsync` keeps its `follow` flag, because it is a faithful wrapper of `docker logs`, which has one; the window is what decided.
- **A follow stream ends when the container does, so its clean end is not the end of the window's job.** `docker logs --follow` returns the moment the container stops and does not resume, which would make a `docker restart` silently kill the window. So the window then **watches**: `DockerService.ContainerEventReceived` debounced 400 ms, with a 30 s poll behind it, and one `IsRunningAsync` probe per look. The reconnect is a plain reload rather than an append with `--tail 0` or `--since`, and that is why it can be late without losing anything: docker keeps a container's log **across** a restart, so reloading the last 1000 lines shows the shutdown and the new startup in one piece, with nothing shown twice and no clock comparison. An **error** (a logging driver that cannot be read) does not start a watch: the reason is still there and every host event would retry it.
- **Lines are buffered on the read thread and drained by a 120 ms timer**, and the reason is no longer the one it was written for. Posting per line would have swamped the UI thread when the destination was a `TextBox`; feeding a terminal costs one lock and no dispatch at all, which is why the console window feeds straight from its read thread. What the timer buys **now** is that this window's feed runs on the **UI thread**, which is the whole reason `Receive` may move the scroll offset for the hold-your-place rule above: from a read thread that would be a cross-thread read-modify-write racing a scroll bar drag. Each tail's `onLine` still closes over its own token, and that matters more than it did, since a stale line landing in a `StringBuilder` was cosmetic where one landing in a just-replaced parser is not. The 1 MB hand-trim is gone; the cap is `TerminalScreen.MaxScrollback`.
- **Cancelling happens off the UI thread**: `RunSudoCommandStreaming` disconnects its `SshClient` inline on whoever calls `Cancel`. Nothing waits for the reader either.

## Running a command in a container

`ContainerConsoleWindow` is a **real terminal** into `docker exec -it`, opened after `ContainerConsoleDialog` asks what to run and as whom. Non-modal, one per container, closed by `Shutdown`, like a log window.

- **The menu item is gated on `running`, not on `IsRunning`.** `ContainerRow.IsRunning` deliberately includes `restarting`, because Stop and Restart are worth offering on a container coming back up; `docker exec` against one simply fails, so `CanExec` is a stricter predicate rather than a loosening of the shared one.
- **The image is asked what it has before the dialog opens.** `FindProgramAsync` walks `ShellCandidates` (`bash`, then `dash`, then `sh`) in one `docker exec` with `command -v` (a POSIX builtin, so busybox answers it), and the command box starts out holding the full path of whichever it found, so the default is **correct rather than merely likely** and there is no substitution to explain. The probe **always exits 0**, answering with a path or with nothing, because `RunSudoCommand` turns a non-zero exit into an exception and "this image has none of them" is an answer; docker's own failures do still throw. An image with no shell at all is refused before a window that could not start is opened.
- **Only an edited command is re-checked, and then it is checked rather than corrected.** A refusal leaves the dialog up with the text in it, the way `UnattendWindow` stays open when the answer file will not build.
- **The command is split on whitespace with no quote handling**, and the field says so. That covers what the box is for (`/bin/bash`, `bash -l`, `python3 -i`); implementing half of a shell's word splitting would work until it silently did not. An empty **User** passes no `-u` at all, so the image's own user applies, which is a different thing from asking for root.
- **`-e TERM=xterm-256color` is not decoration.** For a `-t` exec the daemon puts a bare `TERM=xterm` into the container, under which a coloured prompt or `htop` falls back to eight colours or none.
- **A clean exit closes the window; a failure keeps it.** Typing `exit` is how somebody says they are finished. This is the opposite of the log window and deliberate: a log is a fact about the container that resumes when it restarts, a session is something the user started and ended. A session that ends by *failing* stays on screen with its reason, which is what **Reconnect** is for.

### The PTY, and why the sudo password is not fed blind

`Services/SshPtySession` is `SshClient.CreateShellStream` on a connection of its own. Nothing existing could carry it: `RunSudoCommandStreaming` is line-oriented and stdout-only, and `FeedSudoPassword` writes the password and then **closes stdin**, which is the one thing an interactive session cannot allow.

- **Nothing is shown until the container is reached.** Getting there means a login shell, so the MOTD, the prompt and sudo's password prompt all arrive first. The session prints a per-session sentinel and **everything ahead of it is buffered and dropped**. The sentinel is printed by a shell *inside* sudo (`sudo -S -p '<marker>' bash -c 'printf "%s\n" "$0"; exec "$@"' '<sentinel>' ...`), so it lands after sudo has authenticated and immediately before the command replaces that shell; printing it before `exec sudo` would put the password prompt on the far side of the gate. Its **newline is load-bearing**: stdout is a terminal and therefore line buffered, so a `printf %s` with nothing after it could still be in the buffer when `exec` throws the process image away. The line ending is skipped with the token, in whichever spelling the pty produced.
- **A session that dies before the sentinel reports the buffer as its reason.** That is the only account there is of a sudo refusal or a missing shell. The buffer is capped, oldest-first, because only the tail of an error matters.
- **The password is written only in answer to sudo's own prompt.** Feeding it blind is safe for a one-shot command, which discards a stdin it is not reading; here stdin is the user's keyboard, so a blind write would type the sudo password into their shell. So `sudo -S -p '<marker>'` with a `Guid` marker per session, which cannot collide with an MOTD or with container output and so needs no time limit on the scan. Buffering everything ahead of the sentinel also removes the need to withhold a partial marker between reads. A **second** sighting means sudo rejected the first answer, so the session ends with `CheckSudo`'s wording rather than spending the remaining attempts. A NOPASSWD host never prints the marker and never sees a byte of the password.
- **The PTY is requested with `ECHO = 0`.** The line typed at the host's login shell and the password that may follow are ours, not the user's, and it costs them no echo: `docker exec -it` puts the terminal into raw mode itself.
- **An argv, not a command line**, rebuilt on the host from a NUL-separated base64 blob, with the rebuilding script itself base64'd, so the only syntax the login shell has to understand is `"$(...)"`. The outer `exec` replaces that login shell, so when the command ends the channel closes rather than dropping the user at a host prompt.
- **Resize is reflection into `ShellStream`'s private `_channel`** (SSH.NET 2024.2.0 exposes no resize), under the fails-soft rule in "Shared idioms". The stated fallback is a terminal stuck at the size it opened with. When it works the SIGWINCH path is real, so `htop` reflows.
- **Disposal goes to the pool thread**, and the session is also disposed when it *ends* on its own, because a window left open on a finished shell would hold a connection for nothing.
- **`Start` is the caller's job.** Both factories hand back an **unstarted** session and both call sites call `Start()` right after subscribing to `DataReceived`. `Open`'s gate would have covered a read thread spawned in the factory, but `OpenShell`'s is open from the first byte, so anything read before the subscription is lost, and on a login shell that is the MOTD and the first prompt. A session abandoned before `Start` disposes cleanly.

### The emulator

`TerminalScreen` keeps scrollback and screen as **one list**, the screen being its last `Rows` entries, which is what makes an ordinary line feed at the bottom a plain append. Scrolling inside a `DECSTBM` region rotates within the region and feeds no history, because a program that set a smaller region is managing its own window. Mutations bump a single `Revision` rather than marking lines dirty, because Avalonia redraws a control whole; the control's 16 ms pump compares it and invalidates only when it moved, which keeps a flood of output from posting to the dispatcher thousands of times a second.

What is implemented is what `vim`, `htop`, `top` and `less` use: the C0 set, `DECSC`/`DECRC`, `RI`, the cursor and erase and insert/delete families, `DECSTBM`, `SGR` including `38`/`48` in both the `;5;n` and `;2;r;g;b` spellings **and their colon forms**, `DSR`, and the DEC private modes for application cursor keys, autowrap, cursor visibility, bracketed paste, the alternate screen and mouse reporting. **Everything else is consumed, never printed**, so the failure mode for something exotic is a missing effect and not a screen full of `[38;5;`. Deliberately absent, each with a comment saying so: sixel, double-width lines, and character sets beyond consuming the selector.

Three things here were bugs waiting to happen:
- **The deferred wrap flag.** Writing to the last column leaves the cursor there and wraps on the *next* printable character. Getting it wrong makes a line drawn exactly to the right-hand edge scroll a blank line, visible in anything that draws a box.
- **A decoded scalar is validated before it reaches a cell.** A truncated or over-long UTF-8 sequence can decode to a lone surrogate or past U+10FFFF, and both make `char.ConvertFromUtf32` throw in the renderer, on the UI thread, with the whole window between it and any catch of ours.
- **Parser replies leave the screen lock before they hit the network.** `Respond` fires inside `Feed`, which runs under `SyncRoot`, and sending goes to a blocking channel write; the control queues them and sends after the lock.

Rendering is **runs of cells sharing a style**, not cell by cell, which would mean eighty `FormattedText` objects per row per frame. Runs of spaces are skipped entirely, and a full screen is mostly those. The cell size comes from measuring a hundred `M`s and dividing, because a monospace face still rounds each advance and measuring one drifts a whole cell across an 80-column line. That measurement is only as good as the face being monospaced at all, which is what `Services/MonoFont` is for and why this control asks it rather than naming a family.

`Ctrl+wheel` font sizing lives in `TerminalControl` itself, checked before the alternate-screen guard so it works inside `vim` and `htop`; setting `FontSize` already relayouts and raises `TerminalResized`, so the far end learns its geometry through the existing debounce. `AppSettings.TerminalFontSize` is read by all three surfaces (both consoles and the log window); `TerminalModule`'s `A-`/`A+` buttons save at once and the wheel gesture is saved from `Deactivate`, guarded on the value having moved so a module switch does not rewrite `settings.json` for nothing.

**The scroll bar stays the host's, and its wiring is `TerminalControl.BindScrollBar`.** Keeping the bar out of the control is what leaves the terminal a plain grid of cells any module could host; putting the *wiring* on the control is what stopped the third host writing the same three lines and the same six line sync method again. What it exists to state once is the mirroring: the bar counts downwards from the top of the history and the control counts backwards from the newest line, so the two are mirrored rather than equal, and getting that the wrong way round drags the view to the far end of the history. A horizontal bar is not mirrored, because both ends count rightwards from the left edge, and which axis a bar is is read off the bar rather than passed in.

**The value is never written back while the bar is the one driving, and that is the fix for a drag that would not keep up with the pointer.** Avalonia treats a thumb drag as a sequence of increments and compensates for a value it did not get: `Track.CalculateThumbAdjustment` compares how far the thumb was asked to move with how far it did move and shifts the `Thumb`'s own drag origin by the difference, so the next pointer move is measured from where the thumb ended up rather than from the pointer. A value the bar was talked out of is therefore never retried, it is **lost**. Rounding to whole lines and writing that back is exactly that, once per pointer event, and a drag is hundreds of them, so the thumb fell steadily behind: dragging from the bottom of a full history to the top meant carrying the pointer a hundred pixels past the top of the window. Letting the bar keep its own fractional value costs nothing, since the offset it is read into is a whole number of lines either way.

### The mouse

`Terminal/TerminalMouse.cs` turns one pointer event into the bytes a program that asked for the mouse expects, or into nothing when the mode it asked for does not cover that event. It sits in Core beside the screen and the parser for the reason they do: which events are reportable and how they are spelled is the terminal protocol, not a toolkit's idea of a pointer. Its output is checked against xterm's documented sequences rather than against itself.

- **Two settings, not one.** Modes 9/1000/1002/1003 say *what* to report and are one setting (`MouseTracking`); 1005/1006/1015 say how to spell it and are a second (`MouseProtocol`). Resetting an encoding falls back to X10 only when it is the one actually in force.
- **A release cannot say which button it was, outside SGR.** Every other encoding writes button 3 and keeps the motion and modifier bits above it, which is also why 1003's bare motion and a release are literally the same bytes under X10. SGR keeps the real button and says "release" with its final letter, which is the whole reason it exists.
- **The X10 encoding gives each field one byte biased by 32, so nothing past column 223 fits.** Such a report is **dropped rather than clamped**: naming the wrong cell is worse than naming none, and anything likely to run in a window that wide asks for SGR.
- **Shift is the escape hatch, and it is not optional.** Holding it hands the pointer back to this end for selecting text; without it there would be no way to copy anything out of a full-screen program.
- **Motion is reported once per cell, never once per pointer event.**
- **A report names a viewport row**, 1-based, because that is the only frame the two ends share. So a press snaps the view to the bottom first. It also floors where the selection code rounds, since a report is about the cell the pointer is inside and a selection is about the boundary it is nearest.
- **A gesture belongs to whoever it started with.** The release is answered from the button this end recorded rather than from the current mode, so a program that turns tracking off between press and release still gets the release it is owed; a selection under way survives tracking being turned on midway; and `OnPointerCaptureLost` ends both, because neither gets a release when another window steals focus and a latched one would make every later hover a phantom drag.
- **A wheel notch is a button** (64 and 65), which is how `less` and `man` scroll at all, and it is reported in every tracking mode. One report per notch: how far that scrolls is the far end's decision, where `ScrollWheelLines` is this end's answer for its own history.
- **The pointer becomes an arrow while the far end owns it**, because an I-beam over a screen that cannot be selected is a lie. The repaint pump reads the mode to decide, since setting it moves no `Revision`.
