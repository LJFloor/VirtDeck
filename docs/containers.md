# Containers

`ContainersModule` is five tabs over one docker host. **Containers** lists what `docker ps --all` reports, creates and edits containers through `Views/Containers/ContainerEditWindow`, starts/stops/restarts/removes them, and can read a log or open a shell. **Images** is the second, **Volumes** the third, **Networks** the fourth and **Stacks** (docker compose projects) the fifth, all four below.

The five tabs are five *subjects* on one host, not five views of one fact, so each carries its own toolbar and its own empty state and only the visible one is polled (the `ServicesModule` rule). What they share is the module's two status slots, one transfer strip along the bottom, and one `_busy` flag. Which tab is on screen is `Current`, and it **clamps** `Tabs.SelectedIndex` into range: that index is -1 transiently, the bool it replaced absorbed that by answering false, and a bare cast would put `(Tab)(-1)` through every switch and match none of them. `ServicesModule` clamps its own for the same reason.

- **`Services/DockerService` is a sibling of `VirshService`, not a layer over it**, written in the same idioms: an `SshConnectionManager` in the constructor, a cached list plus a `ContainersChanged` event, `Task.Run` around blocking SSH calls, queries that swallow and answer empty while mutators throw, and `SpiceLog.Log("[docker] ...")`.
- **Always `sudo docker`.** The login user may or may not be in the `docker` group, VirtDeck already holds a sudo password for `virsh`, and `RunSudoCommand` is the same call either way. Hosts where that is the only option are ordinary rather than exotic: Synology DSM has no `docker` group at all and its socket is root-only.
- **The capability probe is one elevated round trip, and it asks docker about the daemon rather than asking the init system.** `CheckHostCapabilities` emits three tagged records: the client from `docker --version`, which needs no socket and is what `DockerAvailable` and "the test is installed, not running" are read off; the server from `docker version --format '{{.Server.Version}}'`, which *is* the socket; and the compose plugin. It used to be three separate commands, two un-elevated, and the middle one was `systemctl is-active docker`. That only answers on a host whose unit happens to be named `docker`, which is most of them and not all: Synology ships the same dockerd as `pkg-ContainerManager-dockerd`, so a perfectly healthy daemon was reported inactive. Whether the socket answers is the thing the module needs to know and is the same question on every init system and on hosts with none. Asking it makes the probe **elevated**, which is the deliberate departure from `VirshService.CheckHostCapabilities` it used to mirror: a root-only socket has no un-elevated answer to give, and the login window has already accepted the sudo password. The compose half was elevated for its own reason and still is: a CLI plugin is per user, and it is *root's* plugin directory that decides whether `sudo docker compose` works. It is asked here rather than only from the stacks listing because the Stacks tab is disabled without it, and a tab that had to be entered before it could be enabled would never enable. Three daemon states and not two: no client leaves the daemon genuinely unasked (`unknown`), which is a different thing from a client whose socket did not answer (`inactive`).
- **The listing is one round trip** (see the tagged-record idiom). `docker ps --all --no-trunc --format` with a Go template. `{{.State}}` needs docker 20.10 or newer; on anything older the command fails outright and the message reaches the status bar, which beats a state column that quietly says nothing.
- **Uptime is ticked client-side, so the script has to fetch a start time `docker ps` will not give it.** `{{.Status}}` is a rendered phrase ("Up 3 hours"), so the same script adds one **batched** `docker inspect` over the running containers, never one per row: per-VM round-trips were the VM list's original latency problem. It emits **elapsed seconds** rather than a timestamp, so host/client clock skew never enters the number. Two record kinds come back, tagged `c` and `u`. The uptime half is **fenced off from the exit status**, so a host whose `date` cannot parse docker's timestamps still gets its list with the column blank, and docker's own phrase survives as the tooltip on the state cell, which is where a stopped container's exit code still reads.
- **The event tail is `docker events`, filtered, and it is one tail with four subjects.** Repeated values of one key are OR'd and different keys are AND'd, so `--filter type=container --filter type=image --filter type=network --filter type=volume` plus the action list reads as "any of these actions, on a container, an image, a network or a volume". The format is **`{{.Type}}`, not `{{.Action}}`**: the four tables refresh independently and a pull must not re-list the containers, and `create`, `delete` and `destroy` are spoken by more than one type, so the type is the only thing that separates them. The network half adds only `connect` and `disconnect`, because `create` and `destroy` were already in the list: measured on docker 29.1.3 by tailing `--filter type=network` through a create / connect / disconnect / rm / prune cycle, a network speaks exactly `create`, `connect`, `disconnect`, `destroy` and `prune`, there is **no `remove` action**, `docker network rm` emits `destroy`, and `docker network prune` emits a `destroy` per network as well as its own `prune`. The volume half adds nothing to the action list at all: measured the same way, a volume speaks `create`, `destroy` and `prune`, and the `mount` and `unmount` it speaks on every container start and stop are not on the list. Anything that is neither word is ignored rather than falling through to the container refresh. Filtering at all is not cosmetic: unfiltered, `type=container` also carries `exec_*` for every `docker exec` and a `health_status` per health-check interval per container, which on a health-checked host would be a refresh treadmill. It is the one docker stream that carried no `bash -c` of its own, and so the one that had to be routed through `ShellScript.SudoWrap` to pick up the PATH export; the pull and the log tail already wrote their own wrapper and spell the export out in it. One deliberate difference from the libvirt tail: **no `stdbuf -oL`**. That exists to stop virsh block-buffering through libc stdio; the docker CLI is Go, whose `os.Stdout` is unbuffered, and measured, `docker events` already arrives line by line.
- **The CPU and Mem columns are not from the listing, and that is the whole design.** `docker ps` reports no resource usage at all, and the command that does, `docker stats --no-stream`, costs a flat **two seconds** (measured on docker 29.1.3, whatever the container count: the daemon needs two CPU readings a second apart before it can state a percentage). `RunSudoCommand` holds the shared `_ioLock` for its whole call, so folding that into the listing would stall the VM list, the file browser and every other module for two seconds per refresh, on a table the event tail refreshes on every `docker run`. So the two columns are fed by a **second tail**, `StartStatsSampler`, in the shape `HostMetricsService` uses and for the same reason: one remote `while` loop on a streaming connection, which takes no lock, so the cost is one connection rather than a round trip per sample. `--no-stream` in a loop rather than the live stream `docker stats` is by default, because the live one paints a terminal: over a pipe it still writes cursor-home and clear-line escapes around a block it repeats about twice a second, forever, per container. `--no-trunc` is what makes a sample joinable, since otherwise the id is docker's 12-char abbreviation and the listing's is the full 64. An `e` record closes each pass, the way the metrics sampler's awk ends one, and it is what **empties** the columns: the last container stopping is a pass with no rows in it, which is only distinguishable from a silent tail because the marker still arrives.
- **This tail is started and stopped with the page**, which is the one place this module departs from "`Deactivate` leaves event tails running". An event tail is nearly free and its whole value is arriving while nobody is looking; this one asks the daemon to measure every container on the host every few seconds, so it runs while the Containers tab is the thing on screen and not otherwise, which is the same rule as only polling the visible tab. Stopping it **clears the last sample** rather than leaving it on the rows: a container name is still true after a minute on another tab and a CPU percentage is not. The price is the two columns filling in a couple of seconds after the tab is entered, which is one sample's wait. A sample is applied **inside** the row merge, so a row the merge has just created carries its reading before the sort sees it; and a sample landing updates cells without re-ordering the table, exactly as the uptime tick does, because a table sorted by CPU that reshuffled every few seconds would move the row somebody was reaching for.
- **The cells say what docker said, less the part that is noise.** CPU is docker's own percent of one core, so a container busy on two of them reads 200%. Mem draws the **used** half of `2.219MiB / 31.27GiB` and hangs the whole phrase with docker's percentage off the tooltip, the shape the State and Ports cells on either side already have. The percentage is not what the cell draws because it is measured against the container's limit, which for a container that was given none is the host's entire memory, so on most hosts most rows would read `0.00%`. Both columns sort on the number behind the cell (`999KiB` sorts above `1.02MiB` as text) and read it back binary, not decimal: the CLI renders a stats reading with its 1024-based helper and an image size with its 1000-based one, which is why `ContainerRow` parses its own rather than calling `ImageRow`'s. **Blank, never zero**, for a container that is not running, for one the sampler has no reading for yet, and for the `--` docker prints for a container it could not measure: nothing to report is not a report of nothing. The state is tested as well as the sample, because a container that has just stopped is off the next sample but the listing has already said so seconds earlier.
- **The Stack column is one label off the same round trip, not a second question.** `docker ps` will print any label the caller names, so `com.docker.compose.project` rides the listing format between the status and the ports, where it costs nothing and keeps `{{.Ports}}` last: Ports is the one unbounded field on the record and a project name is compose's own `[a-z0-9][a-z0-9_-]*`, so it cannot carry a tab. It sits beside Name because whenever compose chose the name it *is* that name's prefix, and when `container_name:` replaced the name it is the only place the project is stated at all. Blank for every container compose did not create, which is most of them on most hosts, and the search box matches it, so a project name typed there narrows the table to that stack. **`com.docker.compose.oneoff` comes with it**, for the one row where this column and the Stacks tab disagree: a `docker compose run` container carries the project label, so the cell names the project, but it is not one of the project's services and the Stacks tab drops it from the count for exactly that reason. That is said on **hover**, where the tooltip already carries the project in full for a name too long for the cell, rather than in the cell, which would then be saying something other than which project this is.
- **The Ports column says less than docker does, and the tooltip says what docker said.** `{{.Ports}}` prints every published port twice, once for the IPv4 wildcard and once for the IPv6 one, each behind an address that is the same on every row, which made the widest column in the table almost entirely noise. `ContainerRow.CleanPorts` takes three things off it and nothing else: the wildcard addresses `0.0.0.0:` and the IPv6 one in both spellings docker has used (`:::` and `[::]:`), the duplicate entries that collapse once those are gone, and a trailing `/tcp`. So `0.0.0.0:8007->8090/tcp, :::8007->8090/tcp` is drawn as `8007->8090`. A **specific** address is kept, because a loopback-only publish and one exposed on every interface are different facts and this column is the only place either is stated; `/udp` and `/sctp` are kept for the same reason, tcp being docker's default and already what `-p 8007:8090` means. An entry matching none of that is passed through exactly as docker wrote it, the rule `PackageScripts.When` follows for a date it does not recognise: the column's job is to say less, never to say something else. Nothing is lost, because the phrase the host reported is the cell's **tooltip**, which is the shape the State cell one column to the left already has. It is display formatting and lives in the row, so `ContainerInfo.Ports` is still docker's own phrase and nothing in Core knows about any of this.
- **Actions address a container by id, never by name.** A name is the user's own string; the id is checked against `^[0-9a-fA-F]{12,64}$` before interpolation, the same guard `VirshService.DefineVmShell` applies.

## The Docker Hub account

The right-hand end of the **status bar** names the account the host is signed in to, `Views/Containers/HubAccountMenu`, with `Views/Containers/DockerLoginDialog` behind its one command. It is the JetBrains widget a branch name sits in, in the place JetBrains puts it, and it is what turns "the pull failed" into something with a cause on screen.

- **It is in the shell's bar, not in either toolbar, so it is one widget rather than one per tab.** Who the host is signed in to is a fact about the host and not about either table, and the bar is already where this module says what it found on the host (`docker 29.1.3`, two slots to its left). The module owns the instance and hands it over through `IModule.StatusWidget`; the toolbars above are the plain rows of dialog buttons they always were. See the Modules section for what that slot is and what the shell does with it.
- **The dropdown opens upward, hangs off the right edge and squares its hover, and none of the three could be a style.** `JbTopLevelMenuItem` writes `Placement` literally inside its `ControlTemplate`, and a property written that way lands on the template child as a **local value**, which outranks a style setter: a `/template/ Popup#PART_Popup` style is accepted, applied, and silently loses (measured against Avalonia 12.1.1, which still read `BottomEdgeAlignedLeft`). So `HubAccountMenu` sets them from `TemplateApplied`, which is another local value and lands after the template built the child; the corner radius goes with them, because the cell stretches to the bar's full height and a radius would leave the corners of the strip unpainted. The chevron is flipped in the same handler, where a style *would* have worked (the template writes no transform), because which way this thing opens is one fact. Editing the theme is not the alternative it looks like: it would turn every toolbar dropdown in the app upside down to place one widget.
- **Nothing is stored on this PC, because there is nothing to store.** `docker login` writes the credential on the host, where it outlives the command, the SSH session and the app, so the widget only ever reads back what the host already knows and `AppSettings` and the OS secret store are not involved at all. The password lives as long as the call. This is also why `HubUser` is assigned from a **probe** and never from what a login was told: the client never leads the host, so a refused login leaves the widget saying exactly what it said before.
- **Three states, and the `k` tag is what buys the third.** `docker info` prints the account in its **server** section, from the CLI's own reading of the config file, so a host whose dockerd is down prints no such line and an absent name cannot mean signed out on its own. The script echoes `k` when it could ask at all, and without that the widget says **"Login state unknown"** rather than **"Not logged in"**, which is the reading somebody would otherwise act on by signing in again for nothing. Same shape, same reason, as the Images table's Unused column.
- **It is a text probe because there is no field to ask for.** `docker info --format '{{.Username}}'` answers *"can't evaluate field Username in type system.dockerInfo"* (measured on docker 29.1.3): the value never was part of the info payload. So it is `sed` over the printed output, leaning on the C locale for the label, which `RunSudoCommand` exports and which `NeedsForce` already relies on.
- **Login is the one docker call that does not go through `RunSudoCommand`.** That runner puts what it is given on the host's command line, which every local user can read out of `ps`, and base64 would hide it from a glance and from nobody at all. So the password goes over **stdin** through `RunPipeInAsync`, the app's only runner with a writable stdin, exactly as `UserAccountService.SetPasswordAsync` does. `ShellScript.ArrayFrom` is safe inside that body because its loop redirects only its own stdin from a process substitution, leaving the channel's stdin for `docker login --password-stdin`, which reads to EOF; disposing the stream is that EOF. The runner reports an exit status and stderr and never stdout, so docker's `Login Succeeded` is not available here and the exit status is the answer, the same price `LoadImageAsync` pays. **Logout carries no secret and no user text**, so it is the ordinary argv path, and it asks nothing first: it is undone by signing in again, `docker logout` itself asks nothing, and the widget flipping to "Not logged in" is the feedback.
- **No server argument on either**, so both mean the default index server, which is the entry the probe reads back. Other registries are not modelled: `docker info` reports only this one, and listing the rest would mean decoding the host's `auths` map instead of asking the tool.
- **Re-read on every entry, never polled or tailed.** Nothing on the host announces a login, and the thing most likely to change it behind this module's back is somebody typing `docker login` in VirtDeck's own terminal module, so one command per activation is the proportionate answer and there is no Refresh button to add. It is read **after** the table, because the table is what somebody came to look at.
- **Known gap:** a host using a credential helper (`credsStore`) can keep the name in the helper rather than in the config file, and `docker info` then prints no `Username:` line, so the widget says "Not logged in" on a host that is signed in. Reading that back means decoding the auths map and shelling out to `docker-credential-*`, which is a lot for a setup that needs a package installed before it can exist.
