# Containers: images

The second tab: `docker image ls --all`, plus pulling one before anything needs it, moving one to and from this PC as a `docker save` archive, tagging, removing and pruning. `Views/ImageRow`, `Views/Containers/{PullImageDialog,ImageImportDialog,ImageTagDialog}`, `Core/Models/ImageInfo`, and the Images half of `Core/Services/DockerService`.

- **The listing keeps docker's own phrases and asks nothing twice.** One round trip, `{{.CreatedSince}}` and `{{.Size}}` rather than numbers, which is the same rule that keeps `{{.Status}}` on a container row: the age is computed host-side so clock skew never enters it, and the size is what the CLI itself prints. Both columns now sort, so both carry the value they were rendered from beside them: `{{.CreatedAt}}` is one more field on the same listing and costs nothing, and the size is read back into bytes on the client (`ImageRow.SizeBytes`) for the sort key alone, because `docker image ls` exposes no raw byte count and getting one means a batched `docker image inspect` over every image on the host. The cells still draw docker's phrases. Splitting needs no cap, because no field of a docker reference can contain a tab. `--all` is what makes dangling layers appear, which is what Prune is about.
- **Rows merge on id-plus-repository-plus-tag, never on the id.** One image appears once per tag it carries and two dangling layers both read `<none>:<none>`, so an id-keyed merge would collapse rows that are separate lines. A row addresses itself by `repository:tag` where it has one and by id where it does not, which is what makes **removing one of several tags an untag** rather than a delete: docker's own behaviour, and what the confirmation says out loud. There is no state dot, because a container is doing something and an image is a fact; a dangling row is dimmed whole instead, the way a broken symlink is in the explorer.
- **The Status column is the one thing in this table that is not a fact about the image.** Amber "Unused" means no container on the host was created from it, which is exactly what `docker image prune -a` means by unused, so the column says what Prune would take. It is a second best-effort half of the same round trip: one batched `docker inspect` over `docker ps --all --quiet`, never one per row, matched on the **resolved image id**. `docker ps` has no `.ImageID` placeholder and its `.Image` is the reference the container was *created with* (`alpine`, where the image lists as `alpine:latest`, or a tag since moved to another image), so matching that string against a repository and tag would be wrong exactly where it matters; a container's `.Image` is the id, which is what `--no-trunc` prints. Measured against a host of 113 images, all four in-use images were **dangling**, which is the reading a table without the column gets backwards. The amber is the app's transient amber, literal rather than themed for the reason the state dots are, and it is worn by the cell rather than the row, which already carries the dangling dim.
- **Three states, not a bool, and the `k` tag is what buys the third.** The container half is fenced off from the exit status like every best-effort half, so a `docker ps` that fails must not draw every row "Unused": the script echoes `k` when it could ask at all, and without that the column is **blank** rather than confidently wrong. A host with no containers still prints `k`, so "nothing is used" and "nobody knows" stay different answers. It is also why a **container** event refreshes the Images table when that is the one on screen: creating or removing a container is the only thing that flips this column, and the image half of the tail does not carry it.
- **A reference is user text, so no image command interpolates one.** Every one goes through `ShellScript.Argv`/`ArrayFrom` behind a literal `--`, the rule `BuildCreateArgv` already follows. There is no `RequireId` twin here because nothing needs one. (Verified against docker 29: `docker tag`, `docker rmi` and `docker save` all accept the `--`.)
- **`set -o pipefail` is load-bearing on export.** Without it a `docker save` that fails while piped into `gzip` reports gzip's exit status, and what lands is a valid, tiny, empty archive reported as a success (measured: a 20-byte `.gz`, exit 0 without it).
- **`docker save` and `docker load` are the first users of the pipe runners** (`RunPipeOutAsync`, `RunPipeInAsync`), and the host-path import goes through `RunSudoCommandStreaming`. **None of them may use `RunSudoCommand`**, which holds `_ioLock` for its whole call: a multi-gigabyte save through it would freeze every other module. `LoadImageAsync` hands `RunPipeInAsync` a script *body* and never `ShellScript.Wrap`, because piping a script into bash makes that pipe bash's stdin and `docker load` would read an exhausted pipe.
- **`docker load` sniffs its input**, so `.tar` and `.tar.gz` are one code path and the import dialog has no compression question to ask. Export's gzip is the file type in the save picker, so the name and the contents cannot disagree: what the picker returns is read back for `.tar.gz`/`.tgz`, and a name claiming neither has the default appended rather than a gzipped archive landing under a bare name. Since the picker never asked about *that* path, a file already there is confirmed and not replaced.
- **The bar is determinate only where the number is honest.** `MeasureImagesAsync` answers -1 for more than one distinct image, because images share layers and `docker save` writes each once, so summing reported sizes is an upper bound; gzip makes the uncompressed total something other than what lands either way. A bar that stops at 40% on a successful export reads as a failure, so those cases run indeterminate and count bytes instead.
- **Export has one destination, the way a VM export does, and no dialog at all**: the save picker is the whole question, so it is Export, browse, Enter, exporting. Writing to a path on the server was offered here once and was dropped, because it bought nothing `docker save` in a terminal does not already do; an export exists to get an image *off* the host. Import keeps both sources, which is not an inconsistency: a file to load is as likely to be already on the host as on this PC.
- **The export lands through a `.part` rename** (`ExportVmDialog`'s pattern), so what is at the chosen path is either the whole archive or the file that was already there, never a half-written one.
- **Only the host-path import can say what arrived.** `docker load -i` names each image on stdout; `RunPipeInAsync` reports an exit status and nothing else, so the upload path lets the refreshed table be the answer.
- **Force is never taken on this end's initiative.** `docker rmi` is tried plain; only docker's own `(must be forced)` refusal, matched by `DockerService.NeedsForce`, earns the offer, and its dialog's primary is **Leave it**. Prune asks the same way: **Remove dangling only** is the primary and **Remove all unused** the alternative, because the more destructive of two irreversible options must not be the one a reflex chooses.
- **Pull, import and export run in the module, not in their dialogs.** A dialog collects the answer and closes; the module owns the status slots and the transfer strip, which is the one place in the app that draws "something is running and you can stop it". Cancel is issued off the UI thread, because the streaming and pipe runners disconnect their SSH client inline on whoever calls it.
- **Dropping a `.tar`/`.tar.gz` on the module imports it**, handlers on the module root like every other drop target, files only (a directory is not an answer here), and several are imported in turn with the first refusal stopping the rest.
- The Images page has **no Refresh button**, because the tail now carries image events; and its accented command is **Pull**, the one thing on that page that brings something new onto the host.
