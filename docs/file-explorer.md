# File explorer

`FileExplorerModule` browses the host's filesystem: a path bar, one multi-select detail list (Name, Size, Modified, Permissions, Owner, Group, every column sorting), Back/Forward/Up/Home/Refresh and a hidden-files toggle. It **moves and copies on the host** (Cut/Copy/Paste, from the menu and from Ctrl+X/C/V), **uploads and downloads** files and whole trees by command or by dragging them in from the desktop and back out to it, **renames** in the row itself (F2) and **deletes**, permanently and with a confirmation. There is still no viewer, no tree pane and no directory watch.

- **It lists as the logged-in user, and that is the point.** Every other remote file call in the app goes through `RunSudoCommand`, because every one is looking for a VM's disks under root-owned `/var/lib/libvirt/images`. Somebody browsing wants their own view of the machine, so this is the app's only user of `RunCommand`'s non-sudo path for real work. That runner is not a drop-in: it neither wraps its argument in `bash -c` nor exports a locale nor folds stderr, so the script does all three itself.
- **`Services/RemoteFileService` is the one place a remote directory is listed**, and one `elevated` flag covers every caller (this module false, every remote picker true). That is what keeps the `find -printf` format string from existing twice. `ParentPath` and `CombinePath` moved there with it. `RemoteFileBrowserDialog` and `RemotePathBox` take a **`RemoteFileService`**, not a `VirshService`: there used to be a `VirshService.ListDirectory` forwarder they went through, which meant every remote picker in the app depended on libvirt to read a directory, and the containers module needs the same picker with no `VirshService` anywhere near it. `VirshService.Files` is what the VM-side call sites hand over.
- **`%y` and `%Y` are both fetched.** `%Y` is the dereferenced type, so a symlink to a directory is navigable; `%y` is the entry's own, so a symlink is still identifiable, shows its target in the Name column, and is dimmed rather than hidden when `%Y` comes back `N` or `?`. **`%f` is last and the parse splits with a cap of ten**, so a name containing a tab survives; a tab inside a symlink target would mis-split that one row, and names are far likelier to be odd.
- **Sorting and the hidden-files toggle never touch the host.** Both run `PopulateList` over the entries in hand. Directories come first whatever the sort says and the direction applies inside each group; Size orders on the `long`, and **Modified orders on the string**, which is correct because it is formatted host-side as `yyyy-MM-dd HH:mm`, so lexicographic order already is chronological order. A failure latches `_failed` precisely so a sort click cannot replace the reason the list is empty with an empty list.
- **The toolbar is five square icon buttons**, themed `JbIconButton`. Their glyphs are the house 16x16 stroked style, and `IconRefresh` is the app's first arc. **Each glyph binds its `Stroke` to `$parent[Button].Foreground`, not to `JbButtonForeground`**: bound to the brush directly it would stay at full strength while the button is disabled, and Back and Forward are disabled most of the time. With no label left, the tooltip is the only name each button has, so all five say what they do and name their shortcut.
- **The column headers are `Controls/ColumnHeader`**, which is this module's own header cell lifted out once every other table wanted one. This is the one table in the app whose headers are a **two-state** pair: everywhere else a third click drops back to the module's own order, and directories-first here is a convention rather than a nicety, so there is no natural order to return to. See "Shared idioms" for the rest.
- **The selection follows whatever just happened**, which is what makes a listing of several hundred entries usable. Stepping out of a directory selects the one stepped out of; a rename, a paste and an upload all select their result and scroll it into view. `_selectNext` is the one channel for that, a set rather than a name because a paste moves any number of entries, and it holds the names things **landed** under rather than the names they were called (under "keep both" those differ, which is why `PasteOutcome.Landed` and `TransferOutcome.Landed` exist). The navigation half is expressed as "is the place being left below the place being entered?" (`ChildOnTheWayTo`) rather than as a rule about the Up button, so Back, a multi-level jump in history and a typed path all behave alike, a refresh names nothing, and `/etcfoo` is not mistaken for a child of `/etc`.
- **Keys are split between the list and the top level, and focus is what splits them.** Backspace still belongs to the path box, so Backspace-for-Up, Alt+Left/Right and Enter live on the `ListBox` alone. The **commands** cannot: repopulating the list destroys the `ListBoxItem` that had focus, and cutting, deleting and navigating all repopulate, so a list-scoped Ctrl+V would never be seen. Ctrl+X, Ctrl+C, Ctrl+V, F2 and Delete therefore hang off the top level, added on attach and removed on detach. They are registered **bubbling and deliberately not handled-too**, and that is the entire gate: a focused `TextBox` has already consumed all of those, so inside the path box and the rename editor they keep meaning what they mean in any text box, with nothing to test for.
- **`_busy` is one flag for paste, delete, upload and download**: they are the same hazard, each running on a connection of its own and each ending by re-listing the directory underneath it.

## Listing as root

- **The retry is offered on any failure, and never latches.** A path inside a directory the account cannot search is indistinguishable from a missing one to the shell, so refusing the retry on "not found" would strand the user for the wrong reason. What the elevation covers is **one listing**: the next navigation reads as the user again, and while an elevated listing is on screen the status bar says "listing as root". Latching would be fewer clicks in `/root` and a lie everywhere after.
- **The answer is remembered even though the elevation is not.** Pressing the retry records the directory in `_rootApproved`, covering it and everything below it for the session, because walking `/var/lib/docker`, into `volumes`, and back out asked three times for one decision. What is remembered is the **user's answer**, not the elevation: every navigation is still attempted as the login user first, `_shownElevated` still says which answer is on screen. The set is session-only and never persisted, and **no write path reads it**, because agreeing to look inside a directory as root is not agreeing to write into it as root.

## Cut, copy and paste

- **The clipboard is the module's own.** It holds absolute host paths snapshotted at the gesture (a `RemoteEntry` carries no path, and the directory on screen has usually moved by the time Paste is pressed) plus the one bit saying which gesture it was. It deliberately **never touches the desktop clipboard**: a path on the server means nothing pasted into a local application. "Copy path" is the separate command that does put text on the real clipboard. A cut entry is **faded whole** (`RemoteFileRow.IsCut`) rather than only in its name the way a broken symlink is: that one is a fact about the entry, this is a pending change to it, which is the staged-row idiom `VmEditWindow` draws. The fade is read off the clipboard on every rebuild, so it survives navigating away and back, a sort click and the hidden-files toggle.
- **Every question is asked before a byte moves.** `InspectPaste` is one round trip answering whether the destination is still there and writable, whether it sits inside one of the sources, and per source whether the name is taken and what kind each side is; the user settles every clash against that, and only then does `Paste` run. Asking as the copy goes would mean a dialog interrupting a transfer already under way.
- **Two scripts because two runners.** The pre-flight is NUL-terminated tagged records through the ordinary `RunCommand`/`RunSudoCommand` pair. The paste itself is **line**-oriented with every payload field base64'd, because it streams and the callback is a line at a time; base64 is what stops a name containing a newline splitting a record, and each record carries the item's **index**, so a reply is matched by position and never by name (two sources from different directories can share a basename).
- **A folder onto a folder merges, and a paste never deletes what the user did not name.** The conflict dialog's primary is **Replace** for a file and **Merge** for a folder, because that is what happens: `cp -a "$s/." "$t/"` puts the contents in, same-named files are overwritten, and whatever was only in the target stays. Deleting the target first would be the literal reading of "replace" and would destroy files nobody was asked about. The `rm -rf` inside the paste script is of a **move's source**, which is what a move is.
- **A copy back into its own directory has no question to ask, so it is not asked.** It lands beside itself as the first free `name (copy)`, `name (copy 2)`. The free-name loop runs on the host and splits an extension only for a name matching `?*.*`, so `.bashrc` is not turned into ` (copy)` and a directory keeps its whole name. A *move* into the same directory is the no-op it looks like and simply clears the clipboard.
- **`PasteConflictDialog` is a small window rather than a stretched `MessageDialog`**, for two things `Choose` cannot carry: the "do the same for the rest" box, and a disabled **primary**. A file and a folder of the same name is exactly that case, since neither can replace or merge into the other: the primary is disabled with its reason on hover, never hidden, so the dialog asks the same question every time instead of quietly becoming a different one. "Do the same for the rest" still skips a kind mismatch, because there is no overwrite there to apply.
- **Writing offers the same one-shot root retry that reading does.** The retry re-runs only the items that failed, with the answers already given, and `_shownElevated` is untouched. Whether root is worth offering is decided by matching the tool's own words, reliable because the script exports `LC_ALL=C`. A cut is **spent only once the move happened**, so a partly refused one stays on the clipboard.
- **The pre-flight gets the listing's rule too, and not having it was a bug.** Every test `InspectPaste` and `InspectIncoming` make (`-d`, `-w`, `-x`, `-e`) answers **no** for a path whose parent the account may not search, so "not there" and "inside a directory you cannot open" arrive as one verdict. Offering root only on `DestinationDenied` was right for `/var/lib/docker` (whose `-d` succeeds and `-w` fails) and wrong one level down: `/var/lib/docker/volumes` came back `DestinationMissing` and dead-ended with "is gone" on a directory the user was looking at. `RootMightSeeMore` is the predicate now, covering both destination blocks **and** a source the pre-flight could not see (`PasteItem.SourceMissing`, which was set and read by nobody, so a root-owned *directory* read as a missing file and its conflict came back as a bogus `KindMismatch`). `PasteBlock.IntoItself` is deliberately excluded: containment does not depend on who is asking. Declining a blocked plan returns without repeating the reason just read; declining on an unseen source runs anyway, because the host then refuses it by name. **Rename got the same widening**, on `SourceGone` as well as on a denial. `NameTaken` needs nothing, because the elevated run re-does the taken check before `mv`.
- **A paste re-lists explicitly when it finishes**, reusing the expression Refresh runs, because nothing on the host tells a client that a directory changed. It counts into the **status slot** rather than the transfer strip, which is why its `CancellationTokenSource` has no button; wiring it to the strip is a change nobody has made yet.

## Deleting

One `rm -rf` per entry, permanently, with a single confirmation. There is no trash: `gio trash` needs the host's own desktop session and would put files where the person at this end cannot see them, and a VirtDeck-owned trash directory would be a second filesystem to explain.

- **The confirmation is the whole safety mechanism, so it is not optional.** No Shift to skip it, and no per-entry prompt either: the question is asked once, about the whole selection, before anything runs. It names up to five entries and falls back to a count past that (`MessageDialog` is a fixed 420 wide and sizes to its content). A folder is always said to take everything in it, because that is the part somebody can be wrong about. It is `MessageDialog.Confirm` rather than a window of its own, because a delete has neither of the two things that earn `PasteConflictDialog` a window. Enter confirms, because the primary is `IsDefault`: the dialog is modal with nothing to type in it, so Enter is a second deliberate gesture rather than a keystroke carried in from the list.
- **There is no pre-flight, and that is the difference from paste.** A delete has no destination and no conflict. "Is it still there" is answered by `rm -f` itself, which is silent about a path that has already gone and is right to be. "May I" is answered by the run, per entry, and that answer drives the root retry, so asking first would be a round trip and a race for nothing.
- **One script, streamed, in `PasteScript`'s shape** (line-oriented, index-tagged, base64'd payloads, `exit 0`). Streaming is what gives a per-entry counter, a token to cancel and a **message per refused entry**, which is what lets the retry re-run only the entries the host refused.
- **Only the first line of `rm`'s stderr is kept, and the host trims it.** `rm -rf` prints one line per entry it could not remove, so one refused tree can produce thousands, and every line after the first is a consequence of it (`rm` descends, fails on the child, then reports the parent as not empty). The first line is the reason, and it is the line matched for "Permission denied".
- **The script refuses a path with no basename.** The empty string, `/`, a trailing slash, `.` and `..` are all the same test, `${s##*/}`. None of them can occur, since every path is built from the directory on screen and a name out of its listing; `rm -rf` is the command where "cannot occur" is not a good enough reason not to check.
- **`rm` never follows a symlink**, so deleting a link to a directory loses the link and leaves the directory. Worth stating because `RemoteEntry.IsDir` is the **dereferenced** type, so a link to a directory reads as a folder in the list and in the confirmation.
- **The first pass is always as the user**, however the listing was read: being refused is what earns the offer, and a delete is the last thing that should quietly escalate.
- **Cancelling leaves a partly deleted tree, and there is nothing to undo.** A cancelled transfer takes back what it created; what a delete created is absence. So the service catches the cancellation rather than throwing it on and hands back what it got through, the module says so with a count, and the re-list is **not** skipped the way a cancelled paste's is. The Cancel button is there anyway, because the alternative is no way out of a delete of the wrong three hundred entries.
- **It uses the transfer strip rather than the status line**, because it is the one command in the module that cannot be undone and so most needs the button beside it. Progress is over entries rather than bytes, which the bar takes perfectly well.
- **What failed is what gets selected**, since it is still there and is the work left over; a clean delete takes the nearest surviving row instead, read off the rows on screen before the re-list.
- **A deleted path comes off the module's clipboard**, and so does anything that was under a deleted directory. A cut whose every entry is gone stops being a cut rather than becoming an empty one. Same rule as `FollowRenameInClip`.

## Uploading and downloading

`Services/RemoteTransferService` is the only thing in the app that moves a user's files between this PC and the host. It is a sibling of `RemoteFileService`, not part of it: that one is metadata and host-to-host operations, this one is bytes crossing the boundary.

- **One mechanism, `tar` over exec, both directions.** It is the only option covering files *and* whole trees, elevated and not, in one shape: the recursion is tar's, and `sudo` is a prefix. SFTP runs as the login user only, which would leave the one-shot root retry working for listing, paste and rename and not for a transfer, and it depends on the host's sftp subsystem. **It would not buy speed either, so do not rewrite this for one:** measured at **112 MB/s** over gigabit ethernet, about 90% of line rate and roughly the ceiling once TCP/IP, SSH framing and encryption come off. A transfer here is network-bound, which is the opposite of the NBD media path (latency-bound on small reads). GNU tar is assumed, as GNU `find -printf` already is. `RunPipeOutAsync`/`RunPipeInAsync` are the two primitives; `DownloadFileAsync` is now a wrapper over the first, so the read loop exists once.
- **`RunPipeInAsync` must not use `RemoteFileService.Wrap`, and that is not a style preference.** `Wrap` is `echo <b64> | base64 -d | bash`, which makes **that pipe bash's stdin**; a payload command under it inherits the exhausted script pipe instead of the SSH channel and reads nothing, which `tar` reports as "This does not look like a tar archive". Every other script in the app can be piped in because none reads stdin. So `RunPipeInAsync` takes a **script body** and wraps it itself as `bash -c "$(echo <b64> | base64 -d)"`, which hands bash the script as an argument and leaves stdin alone. The download side keeps `Wrap`, because `tar -c` never reads stdin.
- **The elevated upload cannot use `FeedSudoPassword`**, which closes stdin. Writing the password and trusting `sudo -S` to stop at the newline is only half an answer: sudo does read a byte at a time and never over-reads (measured: feed it ten lines with a wrong password and lines four onward are still on the stream), but on a **NOPASSWD** host, or with credentials cached, it does not read stdin *at all*, and the password line would be the first thing `tar` saw. So the client writes `password`, then a per-call `sentinel`, then the payload, and the host skips lines until the sentinel: both cases converge. A *wrong* password needs no handling: sudo spends its three attempts on the next three lines and exits, and the non-zero exit is reported.
- **The upload pre-flight is `InspectPaste`'s destination half.** `InspectIncoming` runs the same `-d`/`-w`/`-x` checks and the same per-name probe, drops the "destination inside a source" loop, and answers the same `PastePlan`, so `PasteConflictDialog` and `ResolveConflictsAsync` settle an upload's conflicts **without changes**. It also returns each name's free `name (copy)`, because a transfer has no host-side loop to resolve `KeepBoth` in; the extension rule is `PasteScript`'s exactly so a copy is named the same whichever route created it, and `FreeLocalName` repeats it on the client for a download. **That field is base64'd on the wire** and sits before the entry name so the name stays the unbounded last field.
- **Extraction finishing is not proof a download worked.** A `tar` that cannot open a member still writes the end-of-archive blocks and exits non-zero, so its stdout is a perfectly valid *empty* archive and the client side sees nothing wrong. The pump task's exception is therefore kept and awaited separately after extraction; without that, a refused download reported success with no files and an empty error message.
- **A cancelled transfer takes back what it created.** Cutting `tar` off mid-entry leaves whatever it was part way through, so cancelling removes the top-level names the transfer brought into being, the way `ExportVmDialog` deletes its `.part`. **Only those**: an entry the user chose to **Overwrite** is left where it is, because the tool truncated the original the moment it opened it and neither end holds a copy, so removing it would destroy what was there before the transfer started. That case cannot be made clean, so it is **named in a dialog** instead of passed over in silence. The `rm -rf` this adds can only reach names the pre-flight reported as free.
- **Cancelling is the only trigger for that.** A transfer that *failed* keeps what did land, because tar extracts the members it can and reports the ones it cannot; that is the same rule paste follows.
- **A transfer retries whole where a paste retries per item.** A paste is a loop the host reports on item by item; a transfer is a single `tar`. Neither touches `_shownElevated`.
- **`-h` and `--no-same-owner`.** Symlinks are dereferenced in both directions (`tar -h` going out; plain recursion coming in, since `Directory.Exists` and `FileStream` follow links): somebody downloading a folder wants the files, it behaves the same on either client OS, and it never asks Windows to create a symlink, which needs a privilege there. The cost is that a cyclic symlink makes tar recurse, which is GNU tar's own caveat under `-h`. `--no-same-owner` because the archive is built here: as root, tar would otherwise restore whatever uid a client-built entry carried.
- **`AttributesToSkip = 0` is load-bearing.** .NET's default `EnumerationOptions` skips `Hidden` and `System`, which on Linux means every dotfile in an uploaded tree would be silently missing. Both the archive walk and the size walk set it, or the bar would run past 100% on a tree it under-counted.
- **Entry names off the host are checked before anything is created.** `Remap` swaps an entry's first path segment for the local name the user settled on, drops anything whose first segment was not asked for, and refuses a `..` anywhere; the resolved path is then required to stay under the chosen directory. A tar's entry names are the far end's to write, so they are input.
- **The transfer strip** is `ConsoleWindow`'s `XferPanel` markup copied, hidden unless something is running, and the service throttles progress to 120 ms so the hop to the UI thread is not paid per 64 KiB chunk.

## Dragging

Three gestures over one set of handlers.

- **Files dragged in from the desktop upload** into the folder row under the pointer, or into the directory on screen when the pointer is not over one. The handlers go on the module root, the idiom all four older drop targets follow, so a drop on the empty space below the last row still lands. `DropFiles.LocalItems` is what allows a directory here.
- **Rows dragged onto a folder row move on the host**, or copy with Ctrl held, reusing `InspectPaste` + `ResolveConflictsAsync` + `Paste` unchanged; `HostMoveAsync` is the shared core Paste now calls too. Only a folder row is a target: dropping on the listing itself would mean moving to where they already are, and there is no `..` row to move up through.
- **The selection is captured on the press, not when the drag starts.** A `ListBox` collapses a multiple selection to the row under the pointer on press, so by the time the pointer has moved far enough the other rows are gone. The press handler is therefore **tunnelled**, ahead of the `ListBox`, and a press inside the existing selection drags all of it while a press anywhere else drags one row.
- **Rows dragged out to the desktop hand over a promise**, `Services/DragOutStaging`. The bytes are fetched into a directory under the temp directory and the drop is given paths to those, because neither platform lets a drag source promise a *stream*: Win32 maps `DataFormat.File` to `CF_HDROP` and Avalonia's OLE wrapper accepts `TYMED_HGLOBAL` only, so there is no `CFSTR_FILECONTENTS` to hang an `IStream` off, and X11 maps it to a `text/uri-list` of `file://` URIs with no `XdndDirectSave0` behind it. Nor can the copy be finished after the drop, because **the source is never told where the target is putting things**: a path handed over half written is a truncated file at the other end. What the platform does give is the *timing*. The value behind a format is fetched **lazily, at the drop**, from `IDataObject.GetData` on Windows and from the X11 selection request, so the bytes have from the press to the drop to arrive. The old note here said none of this was possible; what was actually true is only that a promise has to be one that can be kept in the moment.
- **Two bounds, because that getter runs on the UI thread.** `du -sb` goes first, since the listing's `%s` is a directory's own inode rather than its tree and is therefore the only thing that does *not* know what a folder weighs; over **256 MiB** the fetch is refused before a byte moves, which at the measured 112 MB/s is a little over two seconds and leaves a disk image on the host, where downloading it is a command with a bar and a Cancel button beside it. Everything under the cap gets **ten seconds**, and that timeout is the backstop for the wait as a whole: whatever goes wrong behind it, the getter gives up with nothing rather than hanging the app on somebody else's drop. A refusal is a line in the **status slot** afterwards, because a drag has no hover to put a reason on and the desktop has already said no in its own way.
- **The fetch starts when the drag leaves the module, not when it starts.** That is what keeps a move onto a folder row free: that gesture never leaves, so it never costs a byte. Only a head start, though, never the correctness, since the getter starts it too and a backend raising no leave event simply pays the whole fetch inside the blocking wait. The measurement rides `_shownElevated` the way the download command does, and a permission refusal cannot become the one-shot root retry, because there is nowhere to ask while a drag is in the air.
- **A staged directory outlives its own drag by one.** The desktop may still be reading out of it when `DoDragDropAsync` returns, so it goes when the *next* drag starts; one nothing ever asked for is dropped there and then, `Shutdown` takes the root wholesale rather than stage by stage, and a root left by a pid that is no longer here is swept on the way in.
- **The internal payload is still an in-process format** carrying host paths and nothing else, no text and no files. It is tested first, so an internal move never looks at the staged files, and it cannot leave the app, so a move on the host can never be accepted somewhere that would imply a transfer.
