# Services

`ServicesModule` manages the host's systemd `.service` units: a table per tab, start/stop/restart/reload, an autostart tick per row, mask and unmask. `Views/ServicesModule`, `Views/ServiceRow`, `Core/Services/SystemdService`, `Core/Models/SystemdUnit`.

**Modelled on Cockpit's Services page**, minus its sub-tabs for targets, sockets and timers: only services are here, which is what the tables are sized and worded for. A unit-type filter is the obvious next pass, not a rewrite, since nothing above `SystemdService`'s three scripts names `.service` except the `--type=service` flags and `RequireUnit`'s suffix check.

- **The two tabs are the systemd *scope*, not a filter over one list.** The system and user managers are separate processes with separate unit trees, so a unit name means nothing without saying which, and every method takes a `UnitScope`. This is the one module whose tabs are not two views of one host fact.
- **Listing is un-elevated in both scopes; mutating is elevated in exactly one.** `systemctl list-units` answers anybody, so a read never raises a sudo prompt. Changing the system manager needs root. Changing the **user** manager must never go through sudo: `sudo systemctl --user` addresses *root's* user manager, so it acts on the wrong tree and reports success. `SystemdService.RunArgv` is the one place that branch lives.
- **The journal tail inverts that, and both halves are load-bearing** (`StartEventListener`). `sudo journalctl --user` is forbidden for the same reason, so the user-scope tail runs through `RunCommandStreaming`; but the **system**-scope tail must be elevated, because an account outside `adm` and `systemd-journal` gets only its own entries from `journalctl --system` and gets them *silently*, so an unprivileged system tail looks exactly like a host on which nothing ever happens.
- **`XDG_RUNTIME_DIR` is what makes `--user` work at all.** systemctl finds the user bus at `$XDG_RUNTIME_DIR/bus` and an SSH command channel has no session to inherit it from, so the script exports it for both scopes (inert for `--system`). A user manager exists only while the account has a login session or lingering, so **"there is no user manager" is an ordinary state on a server**: it is carried as `UnitCatalog.ListFailure` in the host's own words, and the module adds the one sentence systemd cannot, that `loginctl enable-linger` is the fix. The version is printed *before* the listing, so "no systemd here" and "this scope could not be read" stay different answers with different empty states.

**Three read scripts, not one, and the split is a measurement.** Against a host with 204 service units: `list-units` **13 ms**, `list-unit-files` **1150 ms**, the batched `show` **460 ms**. The single 1.6 s script this replaced held `_ioLock` throughout and stalled every other module each time it ran. The two slow halves answer what a unit does at *boot*, which changes only when somebody enables, disables, masks or unmasks one.

- **`StateScript` is the cheap pass**, `list-units` only, tags `v`/`e`/`u`, a strict subset of the catalog's so `Parse` handles both with no branch. The poll and the event tail run it. `ReadStateAsync` merges it onto the cached catalog, taking `LoadState`/`ActiveState`/`SubState` fresh and carrying `FileState`/`CanReload` forward; a unit the cache has never heard of sets `StateReading.UnknownUnits`, the cue to pay for a catalog. A cached unit `list-units` did not mention has its run-time half **cleared**, because that is what an empty `ActiveState` already means.
- **`CatalogScript` is the expensive pass** (tags `v`/`e`/`u`/`f`/`r`): first look at a scope, Refresh, and `UnknownUnits`. **Never on a timer.** Its two listings are **merged by name** because neither is a superset: `list-units` knows what a unit is doing now, `list-unit-files` is the only source of `static`, `masked` and `indirect` and of units the manager has never loaded.
- **`ShowScript` is the targeted pass**: every field `SystemdUnit` carries, for a named handful, about 10 ms for one unit. It is what a command reads back instead of reloading its scope, and because it answers `UnitFileState` too, **our own** enable/disable/mask/unmask need no catalog pass. Only a change made outside VirtDeck does.
- `For()` substitutes `SCOPE` **before** `ShowScript`'s `NAMES` blob goes in, because the base64 of an argv can contain the literal string "SCOPE".
- **The `show` pass is handed the names `list-units` just gave, not `'*.service'`.** A pattern there expands over *active* units only: measured, the glob answered for 80 units out of 204 and every inactive one came back with no file state. Word splitting turns the name list into arguments, safe because a unit name cannot contain whitespace (systemd escapes it to `\x20`), with `set -f` so a name is never read as a glob. The block is reassembled into **one self-contained record on the host**, so nothing here depends on the order systemctl printed the properties in.
- **`UnitFileState` from `show` overrides the listing's, and that is what makes a template instance manageable.** `list-unit-files` knows `getty@.service` and never `getty@tty1.service`, so without the override an instance shows no autostart state and refuses to be enabled. The **template itself** is dropped (`SystemdService.Wanted`), since every command against one fails and its instances are listed in their own right; so is a unit file whose state is `alias`, and a `not-found` unit, which is a dangling reference and not a service anybody can act on.

**A journal tail, a 5 second poll and a Refresh button**, a combination no other module has.

- **The tail is `journalctl --follow`, not D-Bus**, and not for want of trying: `busctl monitor` needs `BecomeMonitor`, which the system bus grants to root alone (verified: "Access denied" as an ordinary user), and a bus monitor is not a `Manager.Subscribe()` subscriber, so systemd need not emit the unit signals for it to see. journalctl ships with systemd, needs no subscription, and PID 1 logs every unit job under a stable `MESSAGE_ID`; seven ids cover the vocabulary (start begun/finished/failed, stop begun/finished, reload begun/finished), joined with journalctl's `+`. `stdbuf -oL` is needed (journalctl is C and writes through stdio). The journal itself is the **Logs** module's subject rather than this one's; what is here is the seven message ids and nothing else. See "Logs".
- **The payload is ignored except for one substring test.** `--output=cat` prints the message only, and under `LC_ALL=C` it names the unit ("Started ssh.service - ..."), so the tail raises only for a line containing `.service`. Every SSH connection VirtDeck opens logs a `session-N.scope` line through these same ids, so without that test the app would refresh in response to its own connections.
- **The poll runs `StateScript` alone**, which is why it is *cheaper* at 5 seconds than the old one at 10: about a sixtieth of the shared lock.
- **Refresh is the only way to ask for the expensive pass by name**, which is what makes a `systemctl enable` run outside VirtDeck visible. That is the trade for never paying 1150 ms unasked.

**Commands:**

- **No read flag may gate a command.** Every command used to be ANDed with a module-wide busy flag, so with a 1.6 s pass on a 10 s timer the menu was dead about a sixth of the time and right-clicking gave eight grey items. `UpdateMenu` is now a pure function of the cached rows and the selection. The one control a read flag still touches is **Refresh**, and only the expensive pass sets it: a user pressed that, so a moment of dead is feedback rather than a lie. What replaced the gate is `ServiceRow.Pending`: every `Can*` predicate is false while a command is in flight, which is a row that genuinely is not startable rather than one coinciding with a background read.
- **A command reads back only what it touched, outside every read guard.** `RunActionAsync`/`RunOneAsync` end in `ShowAsync` over their own units: the full reload was 1.6 s of latency before a start showed, and it went through the busy guard, which **silently swallowed it** whenever the poll was in the air. The poll yields to a command, not the reverse. `ShowAsync`'s answer is keyed by the unit's own `Id`, not the name asked for, so it is folded with a loop rather than `ToDictionary`: two requested names that are aliases of one unit come back as one entry.
- **Enable and Disable change boot behaviour only. No `--now`.** Whether a service is running and whether it comes back after a reboot are two questions. The autostart tick carries the file-state word beside it, because a tick alone cannot tell `static` from `disabled`.
- **Mask is the one command that asks first.** It is stronger than disabling and easily forgotten: the unit is linked to `/dev/null` and cannot be started by anything, including as a dependency, and what systemd says when something tries does not point back at this window. Everything else is a `MessageDialog.Info` of the host's words after the fact.

**The table:**

- **The search box is client-side and is the module's answer to its own size.** `--all` lists 250 or more units, and the obvious alternative, an "inactive services" filter, would hide exactly the units somebody opened the page to start. It re-runs `Populate` over the catalog in hand and never costs a round trip, but it is still the most expensive thing this module does on the UI thread, so a keystroke restarts a **150 ms** one-shot timer rather than doing the work. That box is `Controls/FilterBox` now, and this is where its debounce came from; six other tables have one.
- **A tab switch draws the cached table before the round trip that replaces it** (`DrawCached`), since `Page.Catalog` is only ever assigned from a completed read.
- **The two tabs are one `Page` record**, holding scope, list, search box, empty text and menu items; the alternative is two copies of the merge, the filter and eight commands, drifting apart on the first fix.
- Absent systemd rides in the listing as the `v` tag, so there is no separate probe, and a scope that never drew a table is never marked loaded, so its state pass turns into a catalog pass by itself and re-entry re-reads without that being coded twice.
