# User accounts

`UserAccountsModule` manages the host's login accounts: a Users table and a Groups table, add and delete for both, one dialog to add or edit a user, and from it a password, a login shell, a home directory at creation, and group membership. `Views/Users/UserEditDialog`, `GroupAddDialog`, `Core/Services/UserAccountService`.

**The tab strip is the top of the module and each page carries its own toolbar**, as in `VirtualMachinesModule`. A toolbar then only shows what applies to the table under it, which matters here because the system-accounts toggle and the search box are both facts about the user list and would mean nothing above the groups. It also settles which button is accented: that class is for the one command that creates something, so with one create command per page both New user and New group carry it. Refresh is on both pages and is one handler, since a single round trip fills both tables. (The VM module's Networks page gets no toolbar at all, because every network command needs a selection and lives on the right-click menu.)

**Modelled on Cockpit's Accounts page**, and three answers here look like omissions until you know why:

- **There is one kind of group, applied with `gpasswd -a`/`-d`, and the account's own group is not one of them.** Every host VirtDeck manages gives an account a group of its own and names it as the gid on the passwd line, so it is not a membership anybody adds or removes and nothing here can change it. It is therefore left out entirely rather than drawn as a ticked row nothing may untick: out of the edit dialog's list, and out of the users table's Groups column, where it used to lead every row marked `(primary)` and so said the same thing about every account. `UserAccountService.Resolve` is where it comes off, keyed on the gid, which also keeps it out on a host where somebody has additionally written the user into their own group's member list. What survives is one word, "groups", with no primary/secondary vocabulary to explain and no note under the tick list explaining a disabled row. The **Groups tab still counts it**, because "who is in this group" is a different question from "which of my groups may I change": `GroupRow` adds the accounts whose gid names the group to the group file's own member list, or a per-user group would read as having no members. Creation is the one place `useradd -G` is used, because there is no existing membership to diff against; everywhere else the delta is per group, since `-G` replaces the whole set and would silently drop a group added on the host since the dialog opened.
- **The home directory is set at creation and read only afterwards.** Moving one means `usermod -d -m`, which relocates the files and can fail part way across a filesystem boundary or on an open file. The box is disabled rather than hidden, with a note saying why.
- **The Groups tab is unfiltered**, where the Users tab hides system accounts behind a toolbar toggle: `docker`, `libvirt` and `sudo` are all system groups by GID, so a GID filter would hide exactly the rows somebody opens that tab to find.

One divergence: Cockpit *also* hides any account whose shell is `nologin` or `/bin/false`, which hides sftp-only and service accounts that are real accounts somebody has to administer. The filter here is UID only, and it is **the host's own range, both ends** (`UID_MIN`..`UID_MAX` from `/etc/login.defs`, plus root). The upper end is not decoration: `nobody` is uid 65534 and clears `UID_MIN` by a mile. Cockpit reaches the same place by naming `nobody`; the host's own number covers the whole convention, `nfsnobody` included.

**The user name and the home directory follow the full name as it is typed**, which is the Fedora installer's model rather than Cockpit's (which fills nothing in). "John Doe" suggests `jdoe` and "Hans van den Berg" suggests `hvdberg`: the last word whole, prefixed with the initial of every word before it. Anaconda's own `guess_username` takes only the **first** word's initial, which is the same answer for a two-word name and the wrong one for a surname with a tussenvoegsel, where it suggests `hberg`. Keeping every initial gets both right with no word list and no language detection, at the price of a written-out middle name contributing its initial too. `SuggestUserName` sits beside `IsValidNewUserName` deliberately, because a suggestion the app then refuses is worse than none: it folds accents (Jose, not `jos_`), **drops** what the rule disallows rather than folding it to an underscore, and trims a leading character a name may not start with, so "3M Corp" suggests `corp`. Dropping is right there and folding is right in the name box itself, where one character for one keeps the caret in place. See the auto-fill and fold rules in "Shared idioms" for when a box stops following.

The home directory's base is the **host's own** (`useradd -D`, tag `h`), not a hardcoded `/home`: an ostree host says `/var/home`, and where the box was left empty `useradd` picked the base itself, so a box the app fills in has to hold the path the host would have chosen.

- **Always `sudo`, and this is the counterexample to `FileExplorerModule`.** That module is the app's one un-elevated caller because somebody browsing wants their own view of the machine. Here every mutation needs root whatever happens, and the lock state can only be read from the shadow file, so there is one privileged path and none of the retry-as-root machinery.
- **The listing is one tagged-record round trip.** Seven tags: `u` a passwd line, `g` a group line, `s` a shell from `/etc/shells`, `d` a `login.defs` bound, `p` a `passwd -S -a` status, `h` the home base, `v` the tools' presence. Only `getent` carries `|| exit $?`.
- **The passwd and group lines are emitted whole and split on `:` by the client.** No field of either file may contain a colon, so the parse is exact and needs no escaping and no delimiter of our own. Group members then split on `,`, which they equally cannot contain.
- **GECOS is stored raw and edited in place.** The field is `Full Name,Room,Work Phone,Home Phone,Other` and the full name is only element 0, so writing it back rejoins the tail rather than discarding somebody's room number. `GecosHead`/`GecosTail`/`JoinGecos` are public precisely because that is a contract two assemblies share.
- **The capability probe reports presence, not a version, and that is not laziness.** Debian and Ubuntu's shadow-utils build supports no `--version` on any of its binaries: `useradd`, `passwd` and `chage` all answer "unrecognized option" and print usage. The only version on such a host is the package manager's, which is a different question per distro. So the probe is `command -v useradd`, the slot says `shadow-utils`, and a host that does volunteer a version has it shown.
- **No poll and no event tail, so there is a Refresh button**, and `Deactivate`/`Shutdown` are both empty: no timer, no tail, no window, no second SSH connection. `ActivateAsync` still reloads on every return.

## The password path

**A password never touches a command line, and `SetPasswordAsync` is the only thing in this service that does not go through `ShellScript.Argv`.** `RunSudoCommand` puts whatever it is given on the host's command line, where `ps` shows it to every local user; base64 would hide it from a glance and from nobody at all.

So it goes over **stdin**, through `RunPipeInAsync`, which was built for the elevated upload and does exactly what is needed: it writes the sudo password and a per-call sentinel to stdin, and the remote script skips lines until it has seen the sentinel. The payload is `chpasswd`, the body is one `name:password` line, and disposing the stream is the EOF `chpasswd` waits for. `chpasswd` splits on the **first** colon, so a password containing one is fine; a line break is not, and is refused in the dialog and again in the service.

Ordering is load-bearing twice. On create, `useradd` runs first and a failing password step is reported as **what it is** ("the account was created, but"), because the account exists from that point. On edit, the password is set **before** the lock, because writing a new hash clears the `!` that locks an account.

Password quality is the host's business. The dialog checks only that the two boxes agree.

## Deleting

`MessageDialog.Choose` rather than `Confirm`, because a delete has a second question and asking it in a follow-up dialog would put it after the point of no return. **Keeping the home directories is the primary**, which is what Enter presses, because the more destructive of two irreversible options must not be the one a reflex chooses (Cockpit defaults its "delete files" box to unticked for the same reason). Both buttons say "Delete" out loud. The prompt names up to five accounts and falls back to a count past that, because `MessageDialog` is a fixed 420 wide and sizes to its content, and it says that files owned elsewhere stay where they are, still owned by a UID with no name.

A group that is an account's own group cannot be deleted; that refusal is `groupdel`'s to make and is reported in its own words rather than pre-empted.
