# Containers: stacks (docker compose projects)

The fourth tab: docker **compose projects**. It lists every project on the host, whoever created it, writes and edits compose files of its own, and brings a project up, down, or through start/stop/restart. `Views/DockerStackRow`, `Views/Containers/StackEditWindow`, `Controls/{CodeEditor,CodeHighlighting}`, `Core/Models/DockerStackInfo`, and the Stacks half of `Core/Services/DockerService`.

**Modelled on Portainer's Stacks page, including the part of it that looks like a limitation.** Portainer also shows projects somebody brought up by hand and shows them read-only, because it runs in a container and has no copy of the compose file. VirtDeck reaches the host over SSH with sudo, so it can read the file and does; what it will not do is write to a directory it did not create.

- **Discovery is a label scan, and needs no compose plugin at all.** Compose stamps `com.docker.compose.project` on every container it creates, plus `com.docker.compose.service` and the **absolute** `com.docker.compose.project.working_dir` and `com.docker.compose.project.config_files` (verified against `pkg/api/labels.go` upstream). So one `docker ps --filter label=...` answers which projects exist, which containers belong to each and where each one's files are. **`docker compose ls` is deliberately not used**: it discovers projects by exactly that scan, so it would put a hard dependency on the plugin in front of what a plain `docker ps` already carries.
- **The plugin is a CLI plugin, not part of the daemon, so it is genuinely absent on plenty of hosts, and without it the whole tab is disabled.** This is the one page in the app greyed out whole rather than command by command, and the reason is that the three commands it exists for all read the compose file through the plugin: deploy, down and pull. A page left open without them would be a table of things nothing on it could act on. Start, stop and restart *would* still work (they act on containers, and the listing already carries their ids, which is why `LifecycleAsync` keeps a `docker start|stop|restart` fallback), but they are not on their own a reason to open the page, and the same three containers are one right-click away on the Containers tab. Compose is still preferred for them wherever it is present, because it honours `depends_on` and the fallback cannot.
- **The disabled tab still states its reason on hover, and it is the app's one use of `ToolTip.ShowOnDisabled`.** Everywhere else a disabled control hangs its tooltip off an enabled parent `Border` (`CheckRow`, `ServiceRow`, `MessageDialog`'s alternative button), because a disabled control is not hit-testable. A `TabItem` has no such parent, and Avalonia's tooltip service checks `IsEffectivelyEnabled || ToolTip.GetShowOnDisabled(control)`, so the attached property is exactly the escape hatch for this case.
- **Compose is therefore probed by `CheckHostCapabilities` and not only by the listing.** A tab that had to be entered before it could be enabled would never enable. The probe runs **through sudo**, unlike the docker and daemon probes beside it, and that is not incidental: a CLI plugin is per user, every docker command this service runs is elevated, so it is *root's* plugin directory that decides whether `sudo docker compose` works. It raises no prompt, because the sudo password was accepted at the connect window. The listing keeps its own `v` tag on top of that, so a plugin installed or removed while the page is open is picked up without waiting for the next activation, and **every activation re-probes while the answer is no**, so installing it mid-session is not a dead end.
- **A project that is fully down has no containers, so it has no labels, so docker itself cannot see it.** That is why Portainer keeps a database, and why `DockerService.StacksRoot` (`/var/lib/virtdeck/stacks`, one subdirectory per stack holding one `docker-compose.yml`) exists: **the directory is the state**. It is on the host and not in `settings.json` for the reason the Hub login is not stored either, that the fact belongs to the machine being managed and two clients pointed at one host must agree. It is a directory rather than an opaque file so it stays legible to somebody at a terminal.
- **The right-hand status slot carries the compose version on this page** (`docker 29.1.3 · compose 2.29.7`) and nothing about compose on the other three, where it would be noise above the images table. There is no "no compose plugin" string to draw: without it the page cannot be opened, and the tab says so instead.
- **The listing is one round trip with six tags**, in `NetworksScript`'s shape: `m` a member container, `w` a project's working directory, `c` a project's config files **and whether the first still exists**, `d` a subdirectory of the stacks root, `k` that `docker ps` could be asked, `v` the compose version. The path labels are two further `docker ps` runs rather than extra columns on `m`, so every record keeps at most one unbounded field and keeps it last; `m` needs no cap on its split at all, because a project, service and container name are each `[a-zA-Z0-9][a-zA-Z0-9_.-]*`, a state is one word and an id is hex. All three runs are inside the one SSH round trip, the way the networks script runs three commands in one.
- **The `c` half tests the file on the host rather than trusting the label.** The labels record where a project's files *were* when it came up, and a checkout can be deleted out from under a running stack, so whether the file is still there is a live question. It is what up and down are gated on; start and stop are not, because they act on containers.
- **The two halves are unioned by project name, and neither is a superset.** Labels describe what is running; the stacks root describes what VirtDeck wrote, deployed or not. `Managed` is then read off the **path** (is the effective compose file under the root?) and never off which half produced the record, so a stack sitting in the root that somebody brought up by hand from a terminal is still correctly ours.
- **A `compose run` container is dropped.** It carries the project label but is not part of the stack, so counting it would put a phantom service in the table. That is what the `oneoff` field on the `m` record is for.
- **Compose is always invoked with the project spelled out in full**: `-p <name> --project-directory <working_dir> -f <file>...`. Resolving a project from its name alone is undocumented behaviour, and both the managed and the discovered case know their paths, so nothing depends on it. The project directory matters as much as the files do, because it is what a relative bind mount and a `.env` resolve against.
- **The `2>&1` on a compose run is load-bearing and its placement doubly so.** `RunSudoCommandStreaming` reads stdout only and compose writes every line of its progress to stderr, so without it a deploy shows an empty transfer strip and looks hung. It goes inside the inner `bash -c` rather than on the `sudo`, so sudo's own stderr is not merged into the transcript, which is `TailLogsAsync`'s rule.
- **A stack gets a state dot where a network does not**, because a stack is a set of containers and so it is doing something, where a network is a fact. It is green only when **every** container is up: half a stack running is amber, because "running" is the wrong thing to tell somebody whose database container died. "Not deployed" and "Stopped" are different answers and both are real, and only the first is what Deploy is for.
- **Rows merge on the project name**, because a compose project has no id at all: the string compose stamps on its containers is the whole of its identity. That is `ImageRow`'s situation and it takes the same answer. Ours sort before discovered ones, for the reason the networks list puts docker's predefined three last.
- **A confirmation is the question and nothing else.** "Take the stack media down?", "Delete the stack media?", and for several the count plus the name list, because there the question does not name what it is about. The one line kept beyond the question is the one it cannot carry: that part of the selection is being left out, which changes what happens. Delete's two buttons already say what its second question is, so the paragraph explaining named volumes went with the rest. `RemoveNetworksAsync` was brought to the same shape.
- **Down and Delete are different commands and the difference is the compose file.** Down removes the containers and the networks compose made and leaves the file, so the stack stays in the list ready to deploy again. Delete removes the file too and the stack leaves the list. So Delete's `Choose` does **not** offer "keep the file" as its primary, which would just be Down under another name: the second question is the **named volumes**, where a stack's data actually lives, and keeping them is the primary because the more destructive of two irreversible options must not be the one Enter presses. Same shape and same reason as the user-account delete's question about home directories. Delete always takes the stack down before removing the file, because doing it the other way round would leave containers nothing in this app can address as a set.
- **`RequireStackName` is what makes a path safe to build**, the twin of `RequireId`: `^[a-z0-9][a-z0-9_-]{0,62}$`, compose's own project-name rule, so the empty string, a slash, a trailing slash and `..` are all refused by one test before `rm -rf` can see them. `SanitizeStackName` folds toward it and sits beside it, because a suggestion the app would then refuse is worse than no suggestion, exactly as `SuggestUserName` sits beside `IsValidNewUserName`. Every command rides `ShellScript.Argv`/`ArrayFrom` on top of that.
- **The compose file is written through `RunPipeInAsync`**, not through `VirshService.WriteFile`'s chunked command-line base64: that one rides the payload on a command line and does not create a parent directory. Reading one back is a `[ -f ]`, a `stat -c %s` against a **1 MiB cap** and a `base64`; the cap is not tidiness, because `config_files` is a path off the host that VirtDeck did not choose and a wrong one must not pull a disk image through the command channel. Missing and oversized come back as **values**, not exceptions, because the window has to draw them.
- **The editor is `AvaloniaEdit`**, the app's code editor, because a `TextBox` has no line numbers and no tab key and YAML is the one format here where a literal tab is a syntax error. `AvaloniaEdit.TextMate` was **not** taken: it would pull the whole TextMateSharp grammar bundle in to highlight one language, and `Styles/Yaml.xshd` does it in sixty lines. That file's colours are **placeholders**: `Controls/CodeHighlighting` replaces every one from the themed `JbCode*` brushes and caches a definition per language and theme variant, because a syntax colour fixed in an `.xshd` would read as syntax on one face and as noise on the other, which is why the link colour and the sixteen terminal colours are themed too. It fails soft, so a definition that will not load leaves the editor plain rather than the window unopenable. This window is no longer the only editor: the answer-file window's thirteen script and markup boxes are the same control, and "Code boxes" under the answer file has what they share.
- **A project cannot be renamed**, so an existing stack's name box is disabled with that on hover: every container, network and volume carries the old name in a label, and compose would build a second set beside the first rather than move anything. The way to change it is to create the new stack and delete the old.
- **The YAML is not validated here.** Compose owns that rule, it changes without us, and its refusal names the line; a validator written here would be a worse copy that eventually rejected something valid. Save and deploy surfaces compose's own words, the way User accounts surfaces `groupdel`'s. The write and the deploy stay separate steps, because a compose file that will not come up is still the file the user typed and losing it to docker's refusal would be worse than the refusal.
- **Dropping a `.yml`/`.yaml` on the tab opens it in the editor** rather than writing it to the host on the spot: it still has to be given a project name, and dropping a file is not saying what to call the thing it becomes. The name is suggested from the file's parent directory, which is what compose itself would have named the project.
- **No Refresh button and nothing added to the event tail.** Compose speaks no event vocabulary of its own: a deploy surfaces as ordinary container and network events, which `OnContainerEvent` already routes to whichever table is on screen. A stack **is** its containers, so a container event is the only thing that ever moves this table.
- **Not here yet:** a stack-scoped log window (each container's log is already one right-click away on the Containers tab), stack-scoped volume listing, and adopting a discovered stack into the stacks root.
