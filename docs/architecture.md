# Architecture

## SpiceClient (protocol engine)
- `Protocol/`: `SpiceConstants` (enums.js), `SpiceReader`/`SpiceWriter` (little-endian span helpers; `U32BE` for LZ/JPEG-alpha sub-headers).
- `Crypto/SpiceTicket`: RSA ticket auth via `RSA.ImportSubjectPublicKeyInfo` + `Encrypt(OaepSHA1)` of `password + "\0"` (server pubkey is a 162-byte DER SubjectPublicKeyInfo). Replaces spice-html5's hand-rolled OAEP.
- `Transport/ChannelSocket`: one blocking `TcpClient` per channel; `ReadExact`; locked `Write`.
- `Channels/SpiceChannel` (base): per-channel socket + dedicated read thread; link handshake; common-message loop (SET_ACK to ACK_SYNC + ACK flow control, PING to PONG, NOTIFY). Subclasses: `MainChannel`, `DisplayChannel`, `InputsChannel`, `CursorChannel`.
- `Imaging/`: `SpiceFramebuffer` (a **pinned** top-down BGRA buffer as `Pixels`/`Scan0`; all access under `SyncRoot`; toolkit-agnostic), `ImageDecoders` (BITMAP, JPEG via Skia, LZ_RGB; **QUIC/GLZ deferred, return null**), `DecodedImage`, `BgraImage.EncodePng`.
- `Audio/`: `IAudioSink` + `AudioSinks.Create()` picks by platform: `WaveOutPlayer` (winmm) on Windows, `PulseAudioSink` (`libpulse-simple`, which PipeWire also provides) on Linux, `NullAudioSink` otherwise. The simple API is **synchronous**, so `PulseAudioSink` hands chunks to a writer thread through a bounded queue (dropping when full) rather than blocking the playback channel's read thread. That thread is the **sole owner** of the `pa_simple*` handle: configure/flush/dispose are posted to it as pending state, so `pa_simple_free` cannot race a write. Mute gates the writes; volume is applied in software (the simple API has none, and touching the app's sink volume would outlive the session in the user's mixer).
  **`prebuf` is the anti-crackle setting.** The guest produces audio at exactly 1x, so the server-side buffer never climbs back on its own; whatever cushion exists when playback starts is the entire jitter budget. `prebuf=0` measured ~40 ms and falling, audibly crackly; `prebuf` = 80 ms of a 200 ms `tlength` measures ~90-120 ms steady on PipeWire. `MSG_PLAYBACK_STOP` therefore **drains rather than flushes** (spice-gtk corks for the same reason); only mute flushes, because there the user wants silence now.
- `Interop/NativeLibraryResolver`: maps bare DllImport names to real filenames per platform (`libusb-1.0.dll` vs `libusb-1.0.so.0`, `libpulse-simple.so.0`). There can be only **one** resolver per assembly, so every native dependency registers here. `LIBUSB_OPTION_USE_USBDK` is **Windows-only**; setting it elsewhere fails and would silently disable redirection, so `LibUsbContext` gates it (`CaptureAvailable`).
- `Imaging/IFramebufferSource`: what the display control attaches to (`Framebuffer`, `ResolutionChanged`, `FrameDirty`, the three cursor events). `SpiceSession` implements it, and so does the Remote Control module's `RfbSession` in Core, which is why `SpiceFramebuffer` is painted by two protocols and gained `BlitBgra` and `MarkDirty` for a decoder that already holds BGRA rows.
- `SpiceSession`: the facade. Orchestrates channel bring-up, owns the framebuffer, raises events (`ResolutionChanged`, `FrameDirty`, `CursorSet/Hidden/Reset`, `Disconnected`, `StatusMessage`). Events fire on channel threads; subscribers must marshal.
- `CursorShape`: decoded ALPHA cursor (BGRA + hotspot).

## VirtDeck.Core (shared, cross-platform)
- `Services/`: `SshConnectionManager`, `SshPortForwarder`, `VirshService` (sudo via stdin + marker), `DockerService`, `SystemdService`, `UserAccountService`, `RemoteFileService`, `RemoteTransferService`, `NbdServer`, `IsoHttpServer`, `UsbProvisioning`, `OsLabelCatalog`. Image compression is steered at the protocol level, not via `virt-xml`.
- `RemoteDesktop/`: the Remote Control module's engine, toolkit-agnostic like `Terminal/`. `RfbSession` (RFB over any pair of streams: a reader thread, `RfbWriter`'s writer thread, `TightDecoder` over `TightInflater`'s session-long zlib streams) and `RemoteDesktopService` (the X displays, the embedded `AgentBundle` uploaded to `~/.cache/virtdeck`, and starting `virtdeck-agent` there). See [remote-control.md](remote-control.md).
- **A protocol over an exec channel** goes through `SshConnectionManager.OpenPipeAsync` + `Services/SshPipe`: stdin and stdout as binary streams for the life of the command, stderr drained into a tail, its own connection. The PTY below is for people; this is for protocols, and nothing on it rewrites a byte.
- **Interactive commands** go through `SshConnectionManager.OpenSudoPtyAsync`/`OpenShellPtyAsync` + `Services/SshPtySession`, the only bidirectional channel in the app.
- **SSH authentication**: `ConnectWithPassword`/`ConnectWithKey` (host + **port**). Both build a plain `ConnectionInfo` (the base class is not `IDisposable`, unlike `PasswordConnectionInfo`), so the manager owns the credential lifetime: the auth method and the `PrivateKeyFile` are **fields disposed after the client**, never `using`-scoped in the connect call, because `DownloadFileAsync` and the streaming runners each open a second client from `_client.ConnectionInfo` and would otherwise authenticate with disposed key material.
  **The sudo password is a separate secret** (`_sudoPassword`): key auth has no login password, and a NOPASSWD account has no sudo password either (`FeedSudoPassword` tolerates that; sudo simply never reads stdin). `CheckSudo()` runs `sudo -S -p '' true` once from the connect window and **returns a message instead of throwing**, so a wrong or missing sudo password is reported there rather than as a VM list that fails to load.
  `Services/SshKeyDiscovery` scans `~/.ssh` (`%USERPROFILE%\.ssh` on Windows): a file counts as a key when it has a `.pub` sibling **or** its first line says `PRIVATE KEY`, stock names sorted strongest first. `NeedsPassphrase` treats only `SshPassPhraseNullOrEmptyException` as "encrypted"; anything unreadable answers false on purpose, so the connect attempt reports the real error instead of the UI asking for a passphrase that would not help. SSH.NET 2024.2.0 has **no ssh-agent support**, so keys are always read from disk. **The scan is consented, not automatic**: `AppSettings.SshKeyScan` gates it and `HostManagerWindow` is the only caller; see "The scan of `~/.ssh` is asked about".
- `Services/AppSettings`: JSON at `%APPDATA%`/`~/.config` + `VirtDeck/settings.json`, enums written **numerically** so a bad settings file can never stop the app launching. Replaces the old `HKCU\SOFTWARE\VirtDeck` registry storage; `LegacyRegistryImport` migrates it once on Windows. It holds a **list of `HostProfile`** plus `LastHostKey`, and **never a secret**. The five scalars that held the single host before (`Host`, `Port`, `Username`, `AuthMode`, `PrivateKeyPath`) plus `LastServerMediaDir` are still on the class and still written, read only by `Migrate()`, which folds them into one profile the first time a pre-list file is read; they stay for the reason `VmSettings.ClipboardImagesOff` stays.
- `Secrets/` + `Services/SshCredentialStore`: the OS secret store.
- `Imaging/PpmImage`: `virsh screenshot` P6 decoder to raw BGRA.
- `Unattend/`: the answer-file boundary, and the only code referencing the vendored generator.
- `Terminal/`: `TerminalScreen` + `TerminalParser` + `TerminalMouse`, toolkit-agnostic exactly as `SpiceFramebuffer` is.

## VirtDeck.Avalonia (cross-platform UI)
- `Controls/FramebufferView`: the base both remote screens draw through. A 16 ms pump copies only the **dirty rows** from `SpiceFramebuffer` into a `WriteableBitmap` under `SyncRoot`, then `InvalidateVisual`; one `ImageRect` places the picture (`Unscaled`, `Fit` or `Actual`) for the paint and the pointer alike; it owns the exactly-one-cursor state machine. The pump follows the visual tree and the bitmap survives a detach, because the shell detaches a module's content on every tab switch.
- `Controls/SpiceDisplay`: the VM console's `FramebufferView`, `Unscaled` (a 1:1 `DrawImage` with interpolation `None`, exactly as before the base existed), mouse to the SPICE inputs channel, and the full teardown on detach its closing window wants.
- `Controls/RemoteDisplay`: the Remote Control module's `FramebufferView`, scaled, mouse as an RFB button mask.
- `Controls/TerminalControl`: draws `TerminalScreen`/`TerminalParser` and turns keys into bytes. Knows nothing about SSH or docker: bytes in through `Receive`, bytes out through `Input`.
- `Input/TerminalKeyMap`: Avalonia `Key` to the bytes an xterm sends, from the **logical** key. `Input/PhysicalKeyMap`: Avalonia `PhysicalKey` to AT set-1 scancode, from the **physical** one. The opposition is deliberate: a guest OS applies its own layout to a scancode, so there position is the truth, while a terminal wants characters and the layout has already been applied. **Extended keys are `0xE0 | (atCode << 8)`** (PageUp = `0x49E0`), matching spice-html5 utils.js, NOT `0xE0XX`; the key-up high bit is applied in `InputsChannel.SendKey`.
- `Input/X11Keysyms`: Avalonia keys to X keysyms for RFB, where the **local** layout decides the character (the third opposition to the two maps above; see "Keyboard" in [remote-control.md](remote-control.md)).
- `Input/AsciiScancodes`: char to AT set-1 scancode + shift, for "Type clipboard". Replaces `VkKeyScan`, which read the *host* layout; a fixed US table is exactly as correct and equally approximate elsewhere.
- `Input/IKeyboardGrab`: `X11KeyboardGrab` (`XGrabKeyboard`) on Linux so Alt+Tab/Super reach the guest; no-op elsewhere. **Best-effort by design.** The grab **must** be issued on Avalonia's own X display connection: X reports key events during a grab only to the grabbing *client*, and a client is a connection, so a grab on a private `XOpenDisplay` takes every key away from Avalonia. If the display cannot be resolved, report unsupported rather than falling back.
- `Views/`: `Hosts/HostManagerWindow` (the saved hosts and the way in), `MainWindow` (the window) holding `ShellView` (the shell), `ConsoleWindow`, `CreateVmWizard`, `VmEditWindow`, `ExportVmDialog`, `RemoteFileBrowserDialog`, `UsbDeviceDialog`, `Unattend/UnattendWindow`, `Containers/*`, `Users/*`, the module views, the small device dialogs, and `MessageDialog` (Avalonia has no `MessageBox`). Row view-models live beside their window or module (`VmRow`, `ContainerRow`, `ServiceRow`, `RemoteFileRow`, ...); lists are `ListBox` + `DataTemplate`, not `ListView`.
- `Services/FileDialogs`: the one place the WinForms filter string (`"ISO images (*.iso)|*.iso"`) is translated into `IStorageProvider` picker types (XDG portal on Linux). Only local paths are accepted; everything downstream needs a real `FileStream`.
- `Services/DropFiles`: the one place the drag-and-drop dialect is translated. Avalonia 12 replaced `IDataObject`/`DataFormats.FileDrop` with `IDataTransfer`/`DataFormat.File`, so Avalonia 11 snippets do not apply. `LocalFiles` filters to real local files (a directory is not an answer); `LocalItems` is its sibling where a directory **is** one. **X11 drag-and-drop needs Avalonia 12.1+** (12.0.x has no XDND at all), which is why the csproj pins 12.1 as the floor.
  Drop targets: the console window, the wizard's General page, a removable-drive row in `VmEditWindow`, the connect window's key panel, and the file explorer. Not `RemotePathBox`: its path is on the *server*.
- `Services/DragOutStaging`: the sibling going the other way, and the file explorer is its only user. A drag source can hand the desktop nothing but paths to finished local files (`CF_HDROP` through `TYMED_HGLOBAL` on Windows, a `text/uri-list` on X11), and it is never told where the target will put them, so the bytes are fetched into a temp directory first. What makes that a promise rather than a stall is that the value behind a format is fetched **at the drop**, not when the drag starts; what keeps it from being a freeze is the `du -sb` measured against a 256 MiB cap and the ten-second ceiling on the wait, both of them here rather than in the module. See "Dragging" in [file-explorer.md](file-explorer.md).
- `Controls/RemotePathBox`: textbox + "..." opening `RemoteFileBrowserDialog`. Raises `Browsed` (a file was picked) as well as `PathChanged` (per keystroke), and takes a `StartDirectory` used only while the box is empty. `BrowseText` swaps the square "..." for a full "Browse" label where a row needs it.
- `Services/HostClipboard`: the one place the Avalonia clipboard dialect is translated.

### Styles

`Styles/JetBrainsClassic.axaml` is JetBrains Classic UI (Darcula / IntelliJ Light) trim and **the app's single source of visual scale**. It holds replacement `ControlTheme`s for `Button`/`JbToolButton`/`JbIconButton`/`JbColumnHeader`/`JbStatusBarButton`, `CheckBox`, `RadioButton`, `TabControl`/`TabItem` (top-placed; `JbSideTabControl`/`JbSideTabItem` are the keyed left-placed pair, and `JbModuleTabControl`/`JbModuleTabItem` derive from those with a taller row for the module side menu), `JbTableRow`/`JbFormRow`, `JbGroupBox`, and the menu family. It is merged into `Application.Resources`, **not** `Application.Styles`, because resource lookup reaches `Application.Resources` before the `FluentTheme`'s dictionaries; that is what makes the overrides of Fluent's metric keys (`TextControl*`, `ComboBox*`, `ListBoxItemPadding`, `ToolTip*`) win without `/template/` selectors per state.

- **One monospaced family, and it is resolved rather than named.** `Services/MonoFont` answers it and `App.axaml.cs` publishes it as `JbMonoFont` before any window exists; both terminals, the log window, the script and compose editors and the few fixed-pitch table cells all read that one key. **`"monospace"` is a fontconfig alias, so asking for it by name is a Linux-only answer.** It was what every one of those surfaces asked for, it worked here, and on Windows DirectWrite has no such family: Avalonia substituted the default UI font, which is proportional and, since this app bundles Inter, was always going to resolve to something. Nothing errored, which is how it survived to a release. The terminal then measured its cell from that font's `M` and drew narrower glyphs inside those cells, so the prompt spread out, every colour change opened a gap at the run boundary and the cursor sat far right of the text (measured on the real font manager: 100 `M`s of the fallback are 1269.8px against 361.2px for 100 `i`s, where a monospace face gives 842.9 for both). **Linux deliberately keeps the alias**, because there fontconfig is a real font system and that string is the user's own configured answer, so naming a family would override a choice the desktop already made; Windows and macOS take the first installed family from a list ending in one the platform is guaranteed to have. The test for "installed" has to be that the font manager answered *with the name it was asked for*, since an unknown family is substituted rather than refused, and that is also what correctly stops the alias being mistaken for a family.
- **One font baseline: 12.** A bare `TextBlock` defaults to 12 while every Fluent `ControlTheme` sets its own from `ControlContentThemeFontSize` (14), so labels and the fields beside them rendered two points apart. Each retemplated control drops that setter, the dictionary pulls the key to 12, and every metric (24px fields and buttons, 22px tool buttons, a 14px check/radio box, `12,4` table rows) is sized for it. **Fields and buttons share one height (24)**; `App.axaml` pins `ButtonSpinner`/`NumericUpDown` to the same key because Fluent sizes those outside `TextControl*`. Headings (wizard title 15, login 16) are the deliberate exceptions. **Never set a local `FontSize`/`Height` in a view to line controls up; fix the baseline.**
- **The `MenuItem` template keeps a lane for `InputGesture`**, because a retemplate that drops Fluent's gesture column makes that property draw nothing anywhere, including in the cut/copy/paste flyout a `TextBox` brings with it.
- `JbDialogFooter` is the shaded strip that holds an edit, details or wizard window's status text and buttons. Every edit window docks one at the bottom, and a tabbed edit window uses `JbSideTabControl`; small prompts keep a plain button row.
- `JbGroupBox` templates its content inset from `Padding` (12,10 default) so a box whose whole content is a table can ask for `Padding="0"` instead of drawing a second border inside the first.
- **Some brushes sit deliberately outside the theme dictionaries**: `JbGroupBoxBorder`/`JbGroupBoxHeader` are grey with an alpha channel and read on either face, and `JbIconAdd`/`JbIconRemove` must not change meaning with the theme. `JbErrorForeground` *is* themed and is the brush for inline validation text (a message about something the user must change, never an ordinary hint; those are 0.7 opacity), so no view hardcodes a red.
- **State dots** are green usable, amber transient, grey not going anywhere, plus red `#C75450` for a **failed** systemd unit, which is the one list where grey would bury the most important row.
- **`JbLinkForeground` is the one brush for a link out of the app**, themed like `JbErrorForeground` and for the same reason: a hardcoded blue reads as a link on one face and as disabled text on the other. It is JetBrains' own link colour rather than the accent the default button wears, because that accent is a *background* with white on it and is too dark on the light face and too weak on the dark one used as a foreground. There is no link control: Fluent's `HyperlinkButton` brings a button's padding into the middle of a sentence, so a link is a plain `TextBlock` with this brush, an underline, a hand cursor and `TextWrapping="NoWrap"` so its click box stays the width of its text. Inline in a sentence it goes in an `InlineUIContainer` with **`BaselineAlignment="Bottom"`**, which arranges it at its own desired size rather than stretching it to the line (measured) and puts it on the same baseline as the words either side. The alignment is not optional: `EmbeddedControlRun.Baseline` is the control's whole *height*, so the default drops the box's bottom edge onto the line's baseline and the link then rides a descent plus half a line gap high (read from Avalonia 12.1.1). Opening it goes through `TopLevel.Launcher` and **fails soft**: a session on a remote host may have no browser at all, and the whole URL is on screen to be read.
- **A table is a table wherever it appears**: the heading strip (`#11808080` over a `#22808080` rule, `12,3` padding) and the transparent `JbTableRow` body are the same elements in a dialog group box and in the shell. Every cell of a module's heading strip is a `Controls/ColumnHeader`, whose `JbColumnHeader` is flat and derived from `JbToolButton`, so a table whose columns sort looks identical to one whose columns do not until the pointer is over it. It resolves that theme once from the tree it is in rather than binding it dynamically, because a `ControlTheme` is one shared object whose own setters reach the themed brushes; it fails soft, so a header that cannot find it is an ordinary button with the right label on it. **It is the one thing derived from `JbToolButton` that drops its `BorderThickness`**: that 1px border is transparent in every state (hover and pressed set `Background` alone) and exists to give a tool button's pill some air, so on a heading all it did was inset the content, and measured, every heading sat 1px right of the column it heads while the strip stood 2px taller than the ones drawn with plain `TextBlock`s. The strip is **23px** in all fourteen tables.
- The sixteen ANSI terminal colours and the two defaults are **themed** here so the terminal reads on both faces; the other 240 are arithmetic (a 6x6x6 cube and 24 greys) and are not a matter of taste.
