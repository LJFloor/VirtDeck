# Unattended Windows setup (autounattend.xml)

**VirtDeck does not write the answer file; it fills in a form and hands it to [cschneegans/unattend-generator](https://github.com/cschneegans/unattend-generator)**, the MIT C# library behind schneegans.de's online generator, vendored at `third-party/unattend-generator/`. That library already owns the unattend schema, its element ordering, the registry tweak behind each toggle, and the PowerShell payloads for settings with no unattend element. `third-party/unattend-generator/VENDORED.md` has the pinned commit, the three-line local delta and the update procedure; **read it before touching that directory**, because the assembly name is baked into `Bloatware.json`'s `$type` discriminators and the repo's no-em-dash rule does not apply there.

`Views/Unattend/UnattendWindow` is sections on the left, page on the right, ordered as the reference tool orders them. **Seventeen pages cover its twenty-seven sections**, each group box keeping the web tool's exact heading so the mapping back stays legible. It follows the tab-walk rules in "Shared idioms"; both `IUnattendTab.Load`/`Apply` take the whole `UnattendConfig` rather than the group the page owns, because most pages render more than one section.

`Unattend/` in Core is the boundary: `UnattendConfig` is the flat serialisable model (one property per tab group, each in its own file under `Unattend/Model/`, named after the tab that edits it), `UnattendConfigMapper` projects it onto the library's `Configuration`, `UnattendXml.Build` is the single entry point (throws only `UnattendBuildException`), `UnattendCatalog` owns the one `UnattendGenerator` and exposes its lookup tables as `UnattendOption` lists, `UnattendPreset` is the JSON save/load, and `UnattendMedia` wraps the result in the answer disc.

## The page vocabulary

**A page is written in one vocabulary, and none of it is local to the page.** The frame is `HeaderedContentControl` with `Theme="{StaticResource JbGroupBox}"`. `Styles/UnattendPage.axaml` holds the class vocabulary, merged into `Application.Styles`: `.page` and `.options` for the two levels of spacing, `.note` and `.subnote` for dimmed prose (the second indented 21px to sit under the option it belongs to), `.under` for the subtree one option owns and greys out in a single `IsEnabled` assignment, `.columnheader`, `.error`, and `.script` for a code box (see "Code boxes" below). **A page that declares its own `UserControl.Styles` will drift from the other sixteen.**

**`RadioButton.GroupName` is scoped to the window, not the page.** All seventeen pages are constructed at once in one `TabControl`, so two pages using the same name would form a single group and silently uncheck each other. Every name is prefixed with its page (`SetupExpress`, `ComputerName`, `ExplorerHideFiles`, ...).

**Four pages render a tickable list from a generator table** (bloatware, desktop icons, folders on Start, visual effects). They share `CheckRow` and one `DataTemplate` in `App.axaml`'s `Application.DataTemplates` (the user-accounts group list is the fifth user, through `CheckRow`'s plain `(id, label, checked, enabled, hint)` constructor beside its `UnattendOption` one; `Hint` is null on all four answer-file pages), and differ only in the catalog and the `WrapPanel.ItemWidth`. `CheckRow.From`/`CheckedIds` convert between rows and the `List<string>` of ids. In all four the tick list is the **whole** setting rather than a set of overrides: the mapper expands it to on/off pairs across the entire table, because Windows replaces its own list rather than merging.

**Two pages are add/remove lists instead** (`ScriptRow`, `ComponentXmlRow`). Both rows notify because **one of their own cells narrows another**: a script editing the default user's hive can only be `.reg`/`.cmd`/`.ps1`, and a component only has settings in some passes. The row coerces its selection *before* announcing either change, or the `ComboBox` sees a moment where its selection is not in its items and clears itself. The narrowing is a courtesy; the rule lives in the generator (`ScriptExtensions.GetAllowedTypes`, `Component.Passes`) and the mapper lets it refuse, because quietly running somebody's VBScript through a different interpreter is worse than saying no.

**The pickers are `ComboBox`es filled through `Views/Unattend/OptionBox`**, which selects and reads back by id so no page repeats the find-by-id pair; `UnattendOption.ToString` is what lets them work with no `DataTemplate`. An id the catalog does not have clears the box rather than falling back to its first entry, so an unanswered picker is visibly unanswered. `UserLocales` is 686 entries and `GeoLocations` 267; swapping in `AutoCompleteBox` is a known refinement, not a correctness problem.

## Code boxes

**Thirteen boxes across eight pages hold something written in a language**, and every one of them is the `AvaloniaEdit` editor the compose window uses, with `Classes="script"` and a language: PowerShell on the computer-name, wallpaper and lock-screen scripts, XML on the Wifi profile, the AppLocker policy, the taskbar icons, the Start tiles and each raw-markup row, JSON on the Start pins, Batch on both Windows PE scripts, VBScript on the disk assertion, and whatever the dropdown says on each row of the scripts page. `Controls/CodeEditor` and `Controls/CodeHighlighting` are the whole of it; the pages say only what they hold.

- **The language is an attached property, not a control of our own.** A `TextEditor` subclass would have to re-point AvaloniaEdit's control theme at itself and would make the one hard case no easier: the scripts page has a language dropdown per row, so its editors are in a `DataTemplate` and learn what they hold **from the row**, which is a binding. `CodeEditor.Language` is that binding target, and setting it is what configures the box.
- **`TextEditor` has no bindable `Text`** (12.0.0 registers `Document`, `SyntaxHighlighting` and `IsReadOnly`, and no `TextProperty`), so the two rows that live in a `DataTemplate` own a `TextDocument` and bind that instead. It is the better shape anyway: the document survives the template rebuilding the editor around it, and `ScriptRow` goes on raising `Content` from the document's own `TextChanged` so the page's script count still follows what is typed.
- **Three definitions are ours and five are AvaloniaEdit's.** `Styles/Yaml.xshd`, `Batch.xshd` and `Registry.xshd` exist because those three languages are not among the twenty-odd the package ships; PowerShell, XML, JSON and JavaScript are, and are used rather than rewritten. A bundled one is opened as **its own copy from the assembly's resources**, never taken from `HighlightingManager`, which hands out a shared singleton this would then be repainting for the whole process. Those resource names are the one fragile thing here, and the fails-soft rule is what bounds it: a definition that will not load leaves that box plain.
- **One colour table covers all eight languages.** The names each definition uses are distinct enough not to collide, and a single table is what keeps a string green in every box on the page. There are six `JbCode*` brushes and rather more kinds of token, so collisions are deliberate: keywords, operators and XML tags share one, and a YAML key, an XML attribute name, a JSON field name and a shell variable share another, because all four are the name half of a name and value pair. **Punctuation is mapped to no colour at all**, which is not tidiness: AvaloniaEdit's JSON definition paints it black, and black on the dark face is very nearly invisible.
- **A pattern in an `.xshd` is compiled with `IgnorePatternWhitespace`**, so a literal space in one is not part of the pattern. It cost an hour: the registry header rule matched nothing until its spaces were written `\s+`.
- **VBScript gets the Visual Basic definition and diskpart gets the batch one.** Neither is exact and both are close: VBScript is a subset of VB, and a diskpart script takes its `rem` comments, quoted strings and numbers from the batch file it is usually driven from, which is most of what there is to colour. The alternative is a box with no colour in it, which is what an unknown language still gets.
- **Every box is numbered.** A long script in a 120px box is a lot of scrolling and no landmarks, and the number is what a compose refusal or an unattend schema error names. `ShowLineNumbers` is on the `.script` class rather than on the app-wide editor rule, because whether a box is numbered is a fact about the box; the compose editor asks for its own in its own markup. The gutter is `JbCodeLineNumber`, IntelliJ's own gutter grey and deliberately dimmer than the comment colour so the numbers recede behind the code, where AvaloniaEdit's default is a flat `Brushes.Gray` on both faces.
- **A disabled box goes dim from a style**, because most of these sit under a radio button and are inert until it is chosen, and AvaloniaEdit's control theme has no disabled look of its own where every Fluent one does.
- **`MaxHeight` is not only about the page.** It keeps a long script from swallowing the page it is on, and it also bounds what the editor is asked to measure, which a box in a scrolling page otherwise is not.
- **Nothing here validates anything.** These boxes are the same fields they were; what the answer file will accept is still the generator's to say at OK, and the pages that carry a schema note still carry it.

## Two decisions the pages make

**The Windows PE page's destructive option is not its default, deliberately.** Under `WindowsPeMode.Generate` the generator replaces `setup.exe` with a .cmd running diskpart and dism, which wipes the target disk with no confirmation: right for the blank virtual disk the wizard just created, wrong for a VM later pointed at existing storage, and the same window is reachable from both. So the page keeps upstream's `DefaultPESettings` and spells the wipe out beside the opt-in. Two things follow. The **Windows 11 requirements bypass** is a property of `setup.exe`'s own check, so upstream models it as part of `DefaultPESettings` and it ceases to exist once Setup is replaced; VirtDeck keeps the checkbox on the **Setup** page, where somebody installing Windows 11 without a vTPM looks for it, and `UnattendConfigMapper.PESettings` puts the halves back together rather than the pages ordering their `Apply`. And the generated disk assertions **deviate from upstream's record defaults on purpose**: the 100/4000 GiB bounds exist to stop a script wiping somebody's external drive, and a virtual disk is routinely smaller than the lower one, so leaving them on would halt Setup on a fine machine. The empty-disk check is on instead. This does not touch the byte-identity tripwire below, which only exercises `DefaultPESettings`.

**How the machine gets its first account is one radio group of three, not a table plus two checkboxes** (`AccountCreationMode`): OOBE asks for a Microsoft account (the default), OOBE asks for a local one, or the answer file names the accounts. This is one place VirtDeck's UI fits better than the web form's checkbox pair, and the library agrees: `IAccountSettings` has exactly these three implementations, so the mapper is a three-way switch. The accounts table, the nested **First logon** box and the Base64 checkbox hang off one panel under the third option and grey out together; the UI keeps what was typed there in the other two modes. A row's group defaults to **Users**, and the generator **refuses** a table with no administrator unless the built-in Administrator is being activated. `NoAdminNote` therefore sits with the table in `JbErrorForeground` and states the rule; `LocalAccountRow` raises change notification (the only row view model in the app written to rather than rendered from) so the note appears as the group column is edited.

## The answer disc

**It reaches Setup on a second CD-ROM, not inside the install ISO.** Windows Setup runs an implicit answer-file search at the start of every configuration pass, and one entry is the root of removable read-only media, so a separate disc is consumed with no command line and no keystroke. Editing the install ISO is not an alternative: a retail image serves its real tree from **UDF** and its ISO 9660 side holds three entries. `Services/Iso9660Builder` writes a small single-file image, 25 fixed sectors plus the file, around 57 KB for a default answer file: Level 2 for the 18-character `AUTOUNATTEND.XML;1`, plus Joliet because `mkisofs -J`/`oscdimg` is what every answer disc in the wild is made with, and **no El Torito record** so the firmware falls through it to the install medium. It is the inverse of `IsoIdentifier`.

**The disc is written to the host, never streamed over NBD.** An unattended install spans several reboots and libvirt refuses `startupPolicy` on network sources (see `AttachNetworkCdrom`), so a disc that died with the VirtDeck session would leave a domain that will not start at all. `VirshService.WriteFile` uploads it with the base64 idiom, chunked because the payload rides on a command line. It lands at `/var/lib/libvirt/images/<vm>-unattend.iso`; `UnattendMedia` owns that naming rule and `UnattendMedia.IsAnswerIso`, which is how `DeleteVmDialog` knows this is the one CD-ROM it may offer to delete.

## The model, and the two typing rules

**The model is flat and mutable; the library's is neither, and `UnattendConfigMapper` is the only place they meet.** `Configuration` is an immutable eighty-parameter record whose settings groups are sum types, and VirtDeck cannot hold one for four reasons: a sum type has nowhere to keep the value typed under the option the user is not on; the settings records validate in their constructors, and a model edited keystroke by keystroke must be allowed to be invalid; `System.Text.Json` cannot round-trip interface-typed members without discriminators, and adding them would mean editing vendored source; and building one needs a live `UnattendGenerator`, which `CreateVmWizard._unattend` must not drag around. So assembling and validating both happen once, at generate time.

The line between the two typing rules is **open set or closed set**, not what the library called it.

- An **open** set is stored as **ids**: a lookup-table entry (locale, keyboard, geo, edition, time zone, bloatware, desktop icon, start folder, component) keeps its `IKeyed.Id`, and so does an enum nobody renders as a fixed row of controls. `ComponentXml.Pass` is the clearest case of the second: which passes are valid is per-component data the catalog answers (`UnattendCatalog.PassesOf`), and `specialize` is the word the generated XML uses. A preset stays readable, and an entry upstream drops degrades to "skipped" instead of a load failure. **Never hand an unchecked id to `Lookup<T>`**, which throws about internal types. Where the id is one **required** value, an unknown one is an **error naming it** (`Lookup`); where it is a member of a set, it is dropped (`Known`). Losing one bloatware removal from a preset is recoverable; silently installing a different locale is not.
- A **closed** set gets a VirtDeck type mirroring it: an enum named `<Thing>Mode` for a radio group, plain bools for a fixed row of check boxes. That covers both which implementation of an `IXxxSettings` interface is selected, which has no upstream name at all (`AccountCreationMode`, `FirstLogonMode`, `LockoutMode`), and small upstream enums that do (`ExpressMode`, `HideFilesMode`, `LockKeyState`, `LockKeyAction`, `StickyKeysMode`). Both are the same shape to the user, and it is an implementation detail of the library that one is an interface and the other an enum. Mirroring also puts the breakage in the right place: an upstream rename stops the **mapper** compiling, which is found immediately, while presets keep loading because they hold VirtDeck's name. Where a name would collide, VirtDeck's changes (`ExpressMode` for `ExpressSettingsMode`, `LockKeyState` for `LockKeyInitial`, `ScriptStage`/`ScriptKind` for `ScriptPhase`/`ScriptType`).

**Anything not yet exposed keeps `Configuration.Default`'s value**, so the answer file only differs from the reference generator's by what the user set. There is one deliberate exception, and it is the tripwire the update procedure checks: the accounts page defaults password expiry to **Never** where upstream leaves Windows' 42 days. Neutralise that one setting and VirtDeck's default output is byte-identical to `Configuration.Default`'s.

## Validation, and the three file buttons

**An invalid config is reachable, so OK validates.** The library validates in the settings constructors and against the unattend schema, and either can say no (no administrator account, a reserved user name, a lockout window longer than the lockout duration). `UnattendXml.Build` is the boundary: the only exception that escapes is `UnattendBuildException`, carrying the library's own wording, which is written for humans. The window builds once on OK, off the UI thread, and **stays open** with a dialog on failure, because the alternative is a wizard that defines the VM, creates its disks, and only then reports that the answer disc could not be written. `CreateVm`'s `Try("Answer disc", ...)` stays as the backstop.

Two constraints are resolved in the mapper rather than by ordering `Apply` calls: the library refuses `KeepSensitiveFiles = false` together with "do not logon" (deleting the answer file is a first-logon command), so `UnattendConfigMapper.KeepSensitiveFiles` keeps the files in that combination; and it refuses disk assertions together with hand partitioning, so `DiskAssertionSettings` drops them and the page greys the group out with the reason. Note the library runs the account policies in the **specialize** pass, not in `FirstLogonCommands`, so unlike the old writer they apply even under "do not logon". What the mapper deliberately does **not** resolve is raw `windowsPE` markup on the Advanced page combined with a generated or custom PE script: that script replaces Windows Setup and everything the answer file would have told Setup to do, so upstream's refusal (which names `$WinPEDriver$` and `drvload.exe`) is passed through and both pages say so.

**Load preset / Save preset / Export XML are not one pair over one format.** All three exchange a file with *this PC* through `FileDialogs`, never through `RemotePathBox`. **Export XML** writes exactly what the disc carries (`UnattendXml.Build` of what the pages say), and it is one-way. **There is no XML import**: the online tool's is server-side code in its web front end, not part of the library, and writing one would mean maintaining a parser for everything twenty-odd tabs can emit against a library that changes. `UnattendPreset` is the answer: VirtDeck's own JSON, a full-fidelity round trip, and it can hold what the answer file cannot, namely the values under the radio options the user is not on. It writes enums **by name** (unlike `AppSettings`) because a preset failure is reportable in a dialog and the file is one somebody may hand-edit, and it insists on a `Version` property, because deserializing straight away would accept any JSON object and answer with pure defaults, which would look like a successful import that quietly blanked every page. `UnattendConfig.Clone()` goes through the same serialiser and self-tests it: anything Clone loses, Save and Load lose too.

**The button is hidden rather than disabled, and it is the one exception to that rule in the app.** Everywhere else a command that cannot run is greyed with its reason on hover, because a command somebody goes looking for must not come and go; nobody looks for this one, so on a Linux VM the row is simply not part of the page. It appears when the guest is Windows and `autounattend.xml` applies to it (so not XP or earlier, which are scripted with `winnt.sif`), Windows-ness coming from `GuestProfile()`. It sits **last on the General page, under Firmware**, which is where a row that appears and disappears costs the least: the fields above it never move. Anything already configured **survives an OS change** and is simply not written, and with the row gone it is the **summary page** that says so.
