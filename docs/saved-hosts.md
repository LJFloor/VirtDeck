# Remembering passwords, and saved hosts

## Remembering passwords

The connect window's three secrets (SSH login password, key passphrase, sudo password) can go to the OS store behind one **Remember passwords** checkbox: the freedesktop Secret Service on Linux, spoken on the session bus, Credential Manager on Windows through advapi32. `Secrets/ISecretStore` + `SecretStores.Create` is the platform seam (the same interface-plus-factory-plus-null-fallback shape as `AudioSinks.Create`), and `Services/SshCredentialStore` is the only thing above it that knows what an SSH secret is. **`settings.json` still never holds a secret**; it holds `RememberPasswords`, and that flag existing is what lets a user who never opted in avoid ever seeing a keyring unlock prompt.

- **Nothing in `Secrets/` throws.** Every path catches and answers falsy, because `Program.Main` appends `ex.ToString()` to the crash log and a store that reports failures by throwing is one bad message away from writing a password to a file. Same reason `Load` answers `""` rather than null.
- **`Save` is an upsert scoped to one account, and it used to be a clean slate.** Forget-everything-then-write-the-form was correct only while `AppSettings` remembered exactly one host, which made the store the state of that one form and staleness impossible with no compare-with-previous code. With a list of saved hosts that premise is gone, and the global wipe would mean connecting to one host deleted every other host's passwords. The delete-then-write survives **within** the identity, for the reason the wipe existed: switching that account between password and key auth must not leave the other mode's secret behind. The **passphrase is only ever written here, never cleared**, since it belongs to the key file and other hosts may share it. **An empty secret is never stored**: "no entry" and "an empty entry" leave the same empty box.
- **`ForgetHost` is the scoped delete, `Forget` the nuclear one.** `ForgetHost` drops one profile's login and sudo entries, and its passphrase **only when no remaining profile names the same key file**, because one key used against three machines has to survive two of them being forgotten. `Forget` still deletes everything VirtDeck saved on this PC (the connect window's Forget button): somebody asking to forget wants the machine clean rather than partly clean. Its named deletes now iterate `AppSettings.Hosts` rather than reading the single remembered host, and the `DeletePurpose` sweep behind them is unchanged.
- **The passphrase is keyed by key file path, the passwords by `user@host:port`.** Host lowercased (DNS is case-insensitive), username not (POSIX usernames are), key path lowercased on Windows only. That identity is `SshCredentialStore.IdentityOf`, and it is public because `HostProfile.Key` **is** that same string: one rule for what counts as one host, so the settings file and the keyring can never disagree, and the host list is deduped by construction.
- **The Secret Service is spoken directly, not through libsecret** (`Secrets/SecretService`, six method calls on one D-Bus object over `Tmds.DBus.Protocol`, which Avalonia already publishes with the app). That dropped an LGPL library, the glib it dragged behind it, a distro dependency the AppImage could not bundle, and a 592-byte `SecretSchema` blitted by hand because C# cannot express its inline `[32]` array without `unsafe`. `SecretService` throws and `LinuxSecretStore` never does: protocol below, policy above.
- **`xdg:schema` is written by hand and must stay.** libsecret added it to the attributes on store *and* search whenever it was given a named schema, and that attribute is the only thing scoping lookups and the purpose sweep to VirtDeck's own items. Writing the same three attributes (`purpose`, `identity`, `xdg:schema`) is also what keeps entries saved by the libsecret version readable by this one, so nobody's saved passwords went missing at the swap.
- **The secret is carried in an encrypted session**, `dh-ietf1024-sha256-aes128-cbc-pkcs7`, negotiated first with `plain` as the fallback, exactly as libsecret did: Diffie-Hellman over RFC 2409's 1024-bit group, HKDF-SHA256 down to 128 bits, AES-CBC, every primitive from the BCL. Both ends encode the numbers shortest-big-endian with no leading zero byte (libgcrypt's `GCRYMPI_FMT_USG`), which is what `BigInteger` writes and the one detail that silently produces garbage if it is wrong.
- **A prompt is a signal, not a return value.** `Unlock`, `CreateItem` and `Item.Delete` answer with a prompt object path when the keyring wants the user; the watch on its `Completed` signal goes on *before* `Prompt` is called, or an instantly answered one completes before anything is listening. After an unlock prompt the code asks `Unlock` again rather than reading the paths out of the prompt's result variant: one round trip on the rare path, and no dependence on a reply shape the implementations disagree about.
- **Calls block** (a locked keyring waits on its unlock prompt), so every call site is `Task.Run` + `Task.WhenAny(work, Task.Delay(TimeoutMs))`, and one `Lock` serialises the store so two secrets queue behind one prompt. A *slow* failure latches the store off for the session: D-Bus spends 25 s activating a name nothing owns, and a save would pay that per slot. The probe asks the bus whether anything owns or can start `org.freedesktop.secrets` before any call is made, so a desktop with no keyring says so instead of paying that timeout even once, and any failure drops the connection so the next call builds a fresh one.
- **Login writes secrets only after `CheckSudo` passes**, so a credential the host rejected never reaches the store. **Save writes them without connecting**, which is the one deviation and is what a site list is for: boxes that refused to store what the user typed until they connected would be decorative, and filling in a host you cannot reach yet is an ordinary thing to do. What Save writes is therefore **unverified by construction**, and the recovery is the one that always existed, now in the same window: the next Login fails, the reason is on the status line, `SelectLikelyStaleSecret` selects the box most likely to be stale, and the Login after that overwrites what was stored.
- **The flag gates reads and writes, not deletes.** Both Forget paths already delete with `RememberPasswords` off, because a delete is what the user asked for; the commit follows that and skips only the reads and the saves.
- **The password boxes are never disabled**, because they are how a connection is made and not only how one is remembered. What `RememberPasswords` decides is whether they are filled in from the store and written back to it, which is still what keeps somebody who never opted in from ever seeing a keyring unlock prompt.
- Both stores protect at rest against another **user**, not another process running as **you**: the Secret Service has no per-application isolation. Say that in the docs, not in the UI.

## Saved hosts

Every host connected to is remembered (`AppSettings.Hosts`, a list of `HostProfile`), and the shell switches between them from a cell at the **left-hand end of the status bar**, `Views/HostSwitcherMenu`. One host is live at a time. `Views/ShellRegistry` owns the process lifetime.

- **A switch builds a new shell and drops the old one; modules are never re-attached.** `Attach` is a one-shot contract and every module is a literal element of the shell's markup, constructed with it, so re-pointing them in place would mean finding and resetting every probed-once latch in all eight (host capabilities, the event tails, the file explorer's working directory and root consents and clipboard, the terminal's live session), and each one missed is a module quietly showing the previous host's data. A new shell is a clean module set with **no reset code at all**. It also settles the throughput readout for free: that figure mixes the per-manager `_ssh.Bytes*` with the process-wide `SpiceTraffic`/`NbdServer` counters, so re-attaching in place would send the delta negative for one tick, while a new shell seeds its baseline in `StartAsync`. **The user sees a switch; the code performs a replace.**
- **The shell is a `UserControl` and not the window, and that split is the whole of what makes a switch seamless.** `Views/ShellView` is the side menu, the status bar, the modules and the connection; `Views/MainWindow` is the OS window around it, and it lives for the session. The replace above used to be a replace of the *window*, which meant carrying its geometry across by hand, and the half that could not be carried is why: a normal window had its `Position`, `Width` and `Height` copied, and a maximized one could only be told to be maximized, with no say in which screen it landed on, so a shell maximized on a second monitor came back on the primary one. Every switch also blinked, took a new taskbar entry and lost focus. None of that was ever load-bearing: the argument above is about the module set, so the module set is what gets rebuilt and the window stays exactly where it is. It removed code rather than adding it, the geometry block and the show-before-close ordering rule both going with it.
- **The new shell goes on screen before the old one is torn down**, which is what the old show-before-close rule was really saying. `ShellView.Shutdown` is synchronous and blocks the UI thread while it closes windows and disconnects clients, so what stands there through it should be the new host's. Assigning `Content` is also what detaches the outgoing modules, and so what unregisters their top-level key handlers (`FilterBox.AttachFindShortcut`, the file explorer's command keys, the terminal's); no module's `Shutdown` or `Deactivate` reads its owner window, so running them detached is safe.
- **The module on screen is carried over, by type.** A switch made from Containers lands on Containers again wherever the new host has docker, which is the difference between a switch and a restart. It is a `Type` off the outgoing `_current` rather than a strip index, so it does not depend on tab order, and reading it off the module is what keeps the shell from naming one. It is applied in `StartAsync` **after** the first probe, since whether that tab exists on this host is exactly what the probe answers; a host without the tooling has no such tab and the user gets whatever `ApplyRelevance` settled on, which is the Overview. `_started` is why that costs nothing: attaching the tree can raise `SelectionChanged` on its own, and without the gate a swap would activate the first tab in the strip, start whatever that module starts, and tear it down a round trip later.
- **A host is saved by connecting to it**, which is the only moment the details are known to be right, and it happens where `AppSettings` was already written: after `CheckSudo` passes. `RememberHost` updates in place or appends, so anything the profile carries that this connect did not mention (its server media directory) survives.
- **`HostProfile.Key` is `SshCredentialStore.IdentityOf`**, so the list key and the secret-store identity are one string. A different account or port on the same machine is a separate host, which is what the store already believed.
- **The switch tries the OS store first and falls back to the connect window.** With the saved secrets it connects with no window and no typing, which is the whole point; with anything missing or refused it opens `HostManagerWindow` on that host, because that window already owns the entire recovery story (a sudo failure reported as itself, the box most likely to hold the stale secret selected) and writing any of it twice would be two versions of it. Nothing is read from the store unless `RememberPasswords` is on.
- **`ShellRegistry` replaced "window closed means process exit".** That was right while the shell could only ever be the one window; a shell can now open a connect window of its own to add a host, and closing it must leave that shell alone. A host switch is not one of those moments any more and never needs to be, since it swaps the shell inside the one window. Both windows register themselves, and the last one out shuts the app down. It also keeps `desktop.MainWindow` off a closed window, guarded on `ShutdownMode.OnExplicitShutdown` because assigning that property is what `OnMainWindowClose` hangs its shutdown off.
- **The menu is four sections and one host-list command.** What this machine is, what to do to it (see "Restarting the host"), which host to be on, and **Manage hosts**, separated. It used to end on **Add host**, **Manage hosts** and **Forget \<this host\>**, which was three routes into one window and a row per host-management verb; the manager owns adding, renaming, repointing and removing, and each of those is a whole story that window already tells, so the cell offers the window rather than shortcuts to parts of it. Forgetting a host is therefore removing its row and committing, which is also what makes the old rule about not offering to forget an unsaved host unnecessary rather than merely unbroken. Forgetting still never touches the live connection, and the cell goes on naming the host you are on: `ShellView._profile` is synthesised from the connection when the list does not have it.
- **The top row is a disabled item used as a fact, not a command**, and that is what a menu has instead of a heading: the distribution the host says it is running (`PRETTY_NAME`). This is the one cell in the shell that is about the machine at the far end, and it is the thing the cell's own label cannot say, that label being the saved host's name or the address it was reached at. It carries **no icon**: the greying, sitting above the first rule and the words themselves are what say it is not a host, and the `MenuItem` theme reserves its 18px gutter whether or not anything is in it, so the label lines up with the host names below regardless. No tooltip either, because a disabled control is not hit-testable and one would never be read. The only art left in the menu is the tick beside the host already connected, and it binds its stroke to the row's own foreground rather than to `JbButtonForeground`, which is what it used to do: bound to the brush it stayed at full strength on a row that is always disabled.
- **That string costs no round trip.** It rides the shell's own module probe (`HostTools`, one un-elevated `command -v` loop that was already sourcing os-release to weigh the package managers), so the shell repaints the cell when the probe answers and only when the answer moved, since that probe runs from a timer. A row with nothing to say is **left out** rather than drawn saying so, which is not the absent-tooling rule being broken: nothing here is a command somebody could go looking for, and a host with no os-release is an ordinary host rather than one missing something.
- **The cell is the shell's, not an `IModule.StatusWidget`.** That slot is for a fact one module owns and takes away with it; which host the whole window is about outlives every module switch. It is `HubAccountMenu`'s markup and `TemplateApplied` fixups almost verbatim, with `TopEdgeAligned**Left**` because it is docked against the left edge. `StatusBarMode` exists because the same control could also sit on an ordinary form, where it would keep `JbTopLevelMenuItem`'s own toolbar metrics and open downward. Nothing uses that mode today: the connect window's list is its own left-hand pane, so the cell it used to carry went with the login form.

### Restarting the host

**Restart** and **Shut down** sit under the name, in the section below the fact row, because they are about the machine at the far end rather than about which machine to be on. They carry the only colour in the menu: the app's own `IconRefresh` glyph in amber, since restart and refresh are the same gesture at two scales, and a red power symbol, both in the 16x16 stroked house style, because they are the only rows here that do something to the machine rather than to what this window is looking at; the tick beside the connected host still binds to its row's own foreground, which is what a glyph that must grey out with its row does. Both open `Views/HostPowerDialog`, which asks two things and runs nothing: how long from now, and what to tell whoever is logged in. `Services/HostPowerService` is what runs it, and `ShellView` is what calls it, for the reason the cell has always known nothing about SSH.

- **Everything goes through `shutdown`, not `systemctl`.** A delay and a message to logged in users are the whole point of the dialog, and `systemctl reboot` has neither. Cockpit's dialog is the shape being followed, down to the message going out as the wall broadcast `shutdown` sends rather than as anything of VirtDeck's own. The systemd path (`systemctl reboot || reboot`) is the fallback for a host without the tool and can only honour the delay, so a message typed for such a host is simply not broadcast: the restart still happens on time, which is the part that was asked for.
- **The delay is a dropdown of fixed values, not a box to type minutes into**: No delay, 1, 5, 20, 40 and 60 minutes, Cockpit's own list minus its "Specific time" row, which is a clock to type into. Every value is one `shutdown +N` takes, so there is nothing to validate and nothing to reject. **One minute is the default**, unlike Cockpit's no delay, because the thing above this dialog is a menu in a status bar rather than a page about the host, and a minute is what gives the wall message somewhere to land.
- **The message is never interpolated into a command.** It is the one field a person types, and it reaches the host as a member of a base64'd argv vector rebuilt on the far side, which is `ShellScript.Argv`'s whole job: apostrophes, backticks and newlines in it are arguments and can never be syntax.
- **The command is detached behind a one second sleep**, for the reason `PackageService.RebootHostAsync` found first: an immediate restart tears down sshd, and with it the channel carrying the command, before it can report anything, so the runner sees a dropped connection and calls a command that worked a failure. A delayed one would return on its own, but it goes the same way rather than being a second shape to get right.
- **A module in the middle of something is said out loud in the dialog rather than being a refusal**, unlike a host switch, which `BusyReason` refuses outright. Switching host halfway through an upgrade is an accident waiting to happen and there is always the option of waiting; restarting the host is sometimes exactly what has to happen, and the app is in no position to decide that it is not.

**What somebody else scheduled shows up here too.** systemd writes `/run/systemd/shutdown/scheduled` for every delayed restart, whoever ordered it: this window, another VirtDeck, a person at a terminal, Cockpit. `HostPowerService.StartWatching` is a **tail**, the shell's own, and it reports within about a second.

- **The loop is on the host, which is what makes it a tail rather than a poll.** Nothing announces this: logind writes the file and says nothing else, and the D-Bus property Cockpit's own page watches needs a bus monitor, which the system bus only lets root be. So the script sits in a one second loop over that file and prints a line **only when the answer moves**, on its own un-elevated connection, self-healing after an SSH blip exactly like the docker event tail. What it costs the host is a stat and a sleep, less than `docker events` sitting idle; what it costs the app is one line per change. A 15 s poll on the shared channel was the first version, and 15 s is what a restart ordered from Cockpit felt like.
- **The first pass always reports**, so starting the watch is also how the current state arrives, and a host with no `/run/systemd/system` says so once and the watcher stops for good rather than reconnecting forever to a host that will never have an answer. `ShellView` still reads the file directly at startup and after ordering or calling off a restart, because those three cannot wait a connection and a second for the tail to say the same thing.
- **The answer is a fact row plus a Cancel row in the menu, and a warning once.** The row says what is scheduled and when, in this PC's clock, converted from the file's absolute epoch so a host in another timezone still lands on the right moment; the command under it is `shutdown -c`. Both are **absent when nothing is scheduled** rather than present and disabled, which is the updates module's restart panel's call and not a hole in the disable-with-a-reason rule: a call-off for a schedule that does not exist is not a command somebody goes looking for.
- **The countdown is recomputed when the menu opens**, off `SubmenuOpened`, because the menu is redrawn only when something changes and a line saying "in 20 min" written half an hour ago would be the one row where that shows.
- **A schedule this window ordered is never reported back as news.** The dialog already said what was going to happen. `_warned` holds the schedule the user has seen and `_ordered` covers the gap where the confirming read fails, which is what an ordered restart's own dropped connection looks like.
- **An immediate `systemctl poweroff` is never seen, and cannot be.** Nothing is written down for it and the host is gone before a poll could read it. That is the honest limit, and it is why the warning says what is scheduled rather than promising the host will not vanish.

### Losing the connection

`Views/ReconnectDialog` is Remote Desktop's reconnect box: when the shared connection drops, it waits for the host with an indeterminate bar and the last attempt's outcome, and Cancel.

- **Seen by a one second check of `IsConnected`**, which reads this PC's own socket and costs no round trip. A restarting host closes the socket and is seen at once; a link that just goes quiet is seen only when TCP gives up on it.
- **Reconnecting replaces the shell, exactly as a switch does**, landing on the same module. Every module's state was about a connection that is gone, and after a restart about a host whose state has moved. `SshConnectionManager.ReconnectAsync` makes the new connection from the old one's credentials, so nothing is asked of the user or the OS store, and **moves** the key and auth method to it, because the old shell's teardown disposes the old connection.
- **It retries without limit, except for refusals.** A booting or stopping host refuses every account but root through `/run/nologin`, so a refused login is retried at a slower pace, and four in a row stop it: retrying one for ever gets an account locked or an address banned on a host that counts failures.
- **Cancel goes back to the way in**, the host manager on this host. `ShellView.IsLost` is what lets Login work there for the host the dead shell was on.

### The connect window

`Views/Hosts/HostManagerWindow` is the saved-host list, the editor for it, **and the app's only way in**. It is what the app opens on, and it is what the status bar cell's one command, **Manage hosts**, opens.

It replaced a separate `LoginWindow`, which was this arrangement inverted: a connect form that happened to carry a host picker, with everything about a saved host implicit behind it. A host was created as a side effect of connecting, named after its own address with no say in the matter, ordered by when it was first reached, and there was no way to fix a typo in an address, repoint one at a different key, change a saved password, or forget a host you were not sitting on. The two windows were also the same field set, the same validation and the same recovery story written twice; the manager is the one that survived, and it took the connect with it.

- **Save, Login and Close, and the third one asks.** Save commits the working copy and stays open; Login commits and then connects, because the host being connected to is the one on screen and leaving the edit uncommitted would connect with details the list does not have; Close asks when anything is uncommitted, since closing this window is also how the app is quit and an edit must not be lost to that silently. A `Closing` handler cannot await, so the close is cancelled and re-issued once the question is answered.
- **With nothing saved it opens on a blank host**, rather than on an empty list with a disabled form and no obvious way in. That is the first-run path, and it is the same row the plus button makes.
- **A blank row is not a host and never becomes one.** `HostRow.IsBlank` is a new row with nothing filled in at all: it is skipped by validation, dropped at the commit, and does not count towards whether anything is uncommitted. Pressing Add host and then changing your mind has to be free, and it is not if an empty row makes Close ask about saving nothing. A row with *anything* in it is validated rather than dropped, so this never swallows a half-typed host; the one exception is the row Login was pressed on, which has to answer for itself even when empty. Login is disabled with its reason while the selected row is blank.
- **Whether anything is uncommitted is computed, never latched.** `IsDirty` compares the rows against what was saved and `HostRow.SecretsDirty` compares the boxes against what the store answered. A flag set in a change handler cannot work here for the reason the auto-fill rule already gives: Avalonia **posts** `TextChanged` and `SelectionChanged`, so a handler runs after the guard around the write that caused it has been lowered, and filling the form in counts as an edit. Latching it got two things wrong, one reported and one silent: Add host followed by Close asked to save nothing, and merely selecting a host with a saved password marked it dirty, so the next Save rewrote its secrets for no reason.

- **It edits a working copy and commits on OK.** `HostProfile.Clone` into a `HostRow` per host, `AppSettings.ReplaceHosts` at the end. Four things want that rather than writing through as the boxes are typed into: Cancel has to mean cancel and `AppSettings` has no rollback, since `Save()` writes the whole object; a live re-key would have to move keyring entries per keystroke; a half-typed row would transiently collide with a saved one in a list that is deduped by construction; and `ShellView._profile` is the *same instance* as the list entry, so a live re-key would change `_profile.Key` under the shell and silently break `SwitchToAsync`'s same-key early return.
- **Editing an address re-keys the profile, and that is the whole difficulty.** `HostProfile.Key` is at once the list's dedupe key, `LastHostKey`, the `login` and `sudo` identity in the OS store, what `ShellView` matches `SshConnectionManager.ProfileKey` against, and what `MediaLocations` matches for `LastServerMediaDir`. So the commit is ordered: repoint `LastHostKey`, `ReplaceHosts`, then the store work with **every delete before every write**. That order is not tidiness: it is what makes a swap come out right, where one host takes an address another has just moved off and row order would delete the entry that had just been written. Two rows colliding on one key is **refused, never merged**, because merging would destroy one row's server media directory and one set of secrets with no undo and no defensible answer as to which wins.
- **No new store API was needed, and `ForgetHost(old, committed)` is why.** It deletes the old `login` and `sudo` entries and keeps the passphrase whenever a surviving profile still names the same key file, which is exactly what a re-key wants: the host moved, the key file did not. Passing the **committed** list is what makes that true, the same ordering `ForgetHost`'s two existing callers already observe.
- **A re-keyed row whose secrets never reached its boxes is backfilled from the old identity first.** Not a corner: the lazy read is capped at `TimeoutMs` and can time out, and remembering may have been switched on after the row was last looked at. Without it the delete would be the whole of the move, which is the "it forgot my password" failure `IdentityOf`'s own comment is written to avoid.
- **The password boxes are read lazily, once per row, and only while remembering is on.** `Load` is the only way to know whether a secret exists, so the read *is* the existence check; doing it for every host up front would put a keyring unlock prompt in front of somebody who opened the window to rename something. The store's own lock serialises the calls, so clicking through five hosts queues behind one prompt rather than five. A stale answer is discarded by a `_secretToken`, because the store blocks and an answer can arrive long after the user has clicked elsewhere, and `SettleAsync` is what stops Login reading a box a keyring has not filled in yet. The boxes themselves are never disabled: see the password rules above.
- **The scan of `~/.ssh` is asked about.** `SshKeyDiscovery.Discover` reads the file names in the user's key directory and the first line of each file that has no `.pub` sibling, and that is somebody's home directory rather than a machine they asked us to talk to, so it is opt-in and the window used to do it unasked on open. The question is put at the gestures that want the answer and never on the way in: `LoadKeysAsync(ask:)` is `false` from `Opened` and `true` from ticking **SSH key** and from the host box losing focus, so a standing yes still fills the dropdown at open while an unanswered one waits for the user to invite it. Filling the form in ticks that radio too, which is what the `_loading` test on the handler is for: selecting a saved key host is not the user asking for anything. Saying no costs the list and nothing else, since a host keeps the key path it was saved with (`SelectKeyFile` adds a path discovery did not find) and Browse and drop are untouched.
- **A row with no address is neither scanned for nor asked about.** The question names the host it would auto-fill a key for, so it cannot be put before there is one, and running the scan anyway would mean reading a key directory on behalf of a row that is not yet a host. That is why the host box is the second trigger: ticking SSH key on a blank new row does nothing, and finishing the address is what makes the question askable, so the ordering does not decide whether the feature happens at all. `LostFocus` rather than `TextChanged`, because nobody wants a dialog after the first letter of a hostname, and `_asking` is what stops the dialog taking focus off that same box and raising a second one behind itself.
- **"Don't ask again" answers both ways, and that is the point of it.** `MessageDialog.Ask` hands back the tick alongside the answer, so it can store a no as readily as a yes; a checkbox that only ever remembered yes would be a second consent button wearing a checkbox. Without the tick the answer holds for the window only (`_mayScan`), which is what stops a second host, or one toggle back to SSH key, re-asking somebody who has already said. Dismissing the dialog from the title bar is a no that stores nothing: closing a question is not an answer to remember. Stored as `AppSettings.SshKeyScan`, a **string tri-state** for the reason `AuthMode` is a string, and **global rather than per host**, because what it answers is about this PC's home directory and not about any machine on the list.
- **Who gets the connection is the caller's business.** `_onConnected` is the login form's old contract kept whole: a new shell on the startup path, `MainWindow.Replace` on a host switch. The window connects, checks sudo, marks the host as the one last connected to, hands the connection over and closes; the shell registry decides whether the process lives on.
- **The shell opens it non-modally, one at a time**, which is what the login form did and for the same reason: the shell stays live and usable, and only gives way once a connection is actually made. `MainWindow.OpenManager` holds the handle so a second click focuses the one already up, and its `Closed` runs `RefreshProfile` then `PaintHosts`, because it can have renamed, added or forgotten a host without ever connecting.
- **`IModule.BusyReason` is checked at the switch, not at this window.** A module mid-upgrade is a reason to refuse tearing a shell down, not a reason to refuse editing a list; `SwitchToAsync` still says so by name when the switcher cell is used, and Login here builds a new shell through `Replace` exactly as it always did.
- **`HostProfile.Name` is free text and is never part of `Key`**, or a rename would orphan the host's secrets. `DisplayName` is the name when there is one and `Address` otherwise, which is the exact expression it held before names existed, so all nine callers read correctly unedited; `Address` is that old expression under its own name; and `Label` is both together, which is what a menu row's tooltip and any prompt that deletes passwords say, because "Home lab" alone does not name the machine. `RememberHost` never writes `Name`, so a connect keeps it. The five computed properties are `[JsonIgnore]`d: `System.Text.Json` writes get-only properties and skips them on the way back in, so they were noise in a file a user may read, and `Key` was actively misleading there, reading as a stored identity when it is derived from the three fields above it.
- **The order is the list's order, with no index field.** Every reader already renders `AppSettings.Hosts` in order, so a stored index would be a second source of truth needing renormalisation on every insert and a defined meaning when duplicated; `RememberHost` still appends, which is where something new belongs. It is also why this is the app's **one table whose columns deliberately do not sort**: the order is the user's and is what the switcher menu shows, so a sortable heading would offer to destroy the feature, and the heading strip is plain `TextBlock`s rather than `Controls/ColumnHeader`.
- **Removing a row asks, even though nothing is destroyed until OK.** The question says when it bites. The alternative is one unremarkable click followed by an OK that deletes the host's saved passwords with nothing in between. A row added in this window has nothing to lose and goes without a question.
- **The window does not register with `ShellRegistry`.** It is a tool window, not a lifetime owner, and registering it would hold the process open on its own.
